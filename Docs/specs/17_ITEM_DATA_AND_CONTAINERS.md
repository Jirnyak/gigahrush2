**Треть таблицы — это заявки на системы, а не поля.** Три группы читаются как

- `contraband_score` + `deceptive_score` — **социальная механика досмотра**,
  которой нет в роадмапе вовсе. Автор её задумал и записал числа.
- `tags_*` — тот самый теговый крафт, который спека 03 проектирует с нуля, **не

  казалось.

  чьё отсутствие означает, что **описания 442 предметов написаны и не видны

**Оценка:** это не мусор и не долг в обычном смысле. Это авторский контент,

`items.csv.future` или явно задокументировать как «данные ждут систему», чтобы
следующий читатель не принял их за живые.

## 3. Ёмкости: 4 слота в контейнере, и это решение

```cpp
// container.h:73-77
inline constexpr int kContainerSlots = 4;
ItemId       item[kContainerSlots]  = {};
std::uint8_t count[kContainerSlots] = {};
```

Четыре слота на контейнер, `count` — один байт, то есть стак до 255.

Труп — отдельный путь: `loot_dead_mobs` стажирует добычу в `CorpseLootPending`, а
`finalize_deaths` переносит в `Corpse.lootSlots` (`loot.h:106`, `loot.cpp:317`).
**Пола на этаже не создаётся** — предмет не падает, он остаётся в трупе.

### 3.1. Переполнение обрезается, и обрезка объявлена

```cpp
// loot.cpp:339-341
pending.slotCount = static_cast<std::uint8_t>(roll_mob_loot_slots(
        ..., static_cast<std::uint8_t>(kMaxCorpseSlots)));
```

Бросок ограничен сверху **на входе**, а не после заполнения, — то есть лишнее не
теряется, оно не бросается вовсе. Разница существенна: молчаливая потеря
предмета выглядит как баг, ограниченный бросок — как правило.

`loot.cpp:568-574` дополнительно пересчитывает `slotCount` по фактически
заполненным слотам после прохода изъятия — **честный счётчик вместо
предполагаемого**. Это правильная форма: счётчик выводится из данных, а не
поддерживается параллельно им.

`loot.cpp:578` закрывает цикл: обысканный труп с нулём слотов помечается.

### 3.2. Четыре слота против инвентаря на 64

Игрок носит 8×8 = 64 слота. Контейнер — 4. Труп — `kMaxCorpseSlots`.

**Следствие для экономики:** контейнер физически не может содержать интересную
находку из более чем четырёх видов предметов, поэтому «схрон» и «склад» не
выразимы через контейнеры. Вместе с выводом [спеки 16](16_ELEVATORS_AND_FLOOR_STREAMING.md)
§4.2 (брошенные предметы не переживают поездку) это означает: **в игре негде
хранить вещи**, кроме собственного инвентаря.

Это не дефект одной подсистемы. Это отсутствующее решение о том, где живёт
имущество игрока между сессиями, и оно всплывает третий раз из третьего
независимого места — как случай «одна дыра, четыре вида» из
[роадмапа](../MASTER_ROADMAP.md).

## 4. Проектируемое

### 4.1. Разделить данные, ждущие систему

```
data/items.csv         — 16 живых столбцов + 11 генераторных
data/items_future.csv  — 14 столбцов, ключ id, с шапкой «данные ждут систему»
```

Причина не в чистоте, а в наблюдаемости: сегодня `durability` в CSV и
`durability` в `ItemDef` выглядят одинаково живыми, и проверить разницу можно
только грепом по потребителям. После разделения вопрос «что не подключено»
отвечается взглядом на имя файла.

**Альтернатива, если разделение сочтено дорогим:** гейт, печатающий список
столбцов без потребителя, при каждой генерации таблиц. Тогда цифра «14 мёртвых»
не расходится с деревом молча.

> **РЕШЕНО 2026-09-30: взята альтернатива, разделение ОТКЛОНЕНО.** Владелец
> выбрал гейт (`csv_columns`), и разделение на два файла не делается вовсе.
> Причина сильнее, чем «дешевле»: `items_future.csv` завёл бы ВТОРОЙ ключ `id`,
> который обязан ходить за первым при каждой правке каталога, — то есть лечил бы
> наблюдаемость ценой дрейфа, ровно того класса, от которого спасает
> `tables_fresh`. Гейт даёт ту же наблюдаемость числом и не создаёт второго
> места, где живёт предмет.

### 4.2. Ёмкость контейнера как свойство типа

```cpp
// БЫЛО: одна константа на все контейнеры.
inline constexpr int kContainerSlots = 4;

// СТАНЕТ: свойство типа контейнера, как и всё остальное в этой игре.
// Шкаф вмещает больше ящика; ящик больше кармана. Четыре типа уже есть.
struct ContainerKind {
    std::uint8_t slots;      // 4 у ящика, 12 у шкафа, 24 у стеллажа
    std::uint8_t valuePct;   // уже существует
};
```

Это разблокирует склад **без** сохранения сущностей: стеллаж на 24 слота в связке
с `FloorStash` из спеки 16 §9.1 даёт игроку место, а формату — 8 байт на запись.

## 6. Явные не-цели

- **Не удалять 14 мёртвых столбцов.** Это авторский контент, опережающий код;
  беспощадная чистка направлена на legacy-хаки, а не на заявки. Пометить —
  да, удалить — нет.
- **Не расширять `ItemDef` за 24 байта ради мёртвых полей.** Пин на 24 байта
  верен; подключать столбец надо вместе с его системой, а не заранее.
- **Не создавать пол-предметы при смерти.** `loot.h:106` объявляет, что добыча
  живёт в трупе, и это дешевле сущностей. Склад решается `FloorStash`, а не
  отменой этого решения.
- **Не поднимать `kContainerSlots` глобально.** Четыре у ящика — правдоподобно;
  проблема в отсутствии **разных** ёмкостей, а не в малости одной.
