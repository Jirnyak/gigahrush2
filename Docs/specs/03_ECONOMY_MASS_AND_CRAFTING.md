## 1. Масса УЖЕ построена и построена правильно — не переделывать

Мандат просил «развитие системы `mass_g`: влияние веса на скорость, выносливость,
шум шагов и силу падения». Это приземлилось **два коммита назад**
(`90fe4ce`, `c8b7dc2`) и сделано лучше, чем формулировка мандата.

Ключевая идея, которую надо сохранить, а не переизобрести
([encumbrance.h:4-37](../../src/game/encumbrance.h)): **вес — не множитель
скорости, а физическое свойство**. Три из четырёх последствий не являются новыми
правилами — это существующие законы, которые наконец увидели ношу:

| Последствие | Механизм | Новое правило? |
|---|---|---|
| Падение больнее | `E = m·v²/2`, `Mass` = тело + ноша | **НЕТ**, закон не менялся |
| Отбрасывание слабее | `p = m·v` | **НЕТ**, закон не менялся |
| Шаг громче | радиус шума × `1 + 0.6·(ноша/ёмкость)` | **НЕТ**, поле шума было |
| Скорость падает | `ёмкость/ноша`, пол `0.35` | ДА, нужен порог |
| Сон тратится быстрее | `+0.10/с` при двойной ёмкости | ДА, нужен порог |

Ёмкость = **64 кг + 4 кг за очко Силы** (`carry_capacity_g`, [rpg.h](../../src/game/rpg.h)).
Единица одна на всё дерево: `mass_g` в целых граммах в `items.csv` (442 строки),
`mobs.csv` (68), `props.csv` (9).

Развёртка сделана со стаггером 1-из-8 по идентичности
([encumbrance.h:40-50](../../src/game/encumbrance.h)) — 27k чтений слотов на тик
превратились в амортизированные, ценой отставания `Mass` на ≤ 64 мс.

**Вывод:** направление 3 — это не масса. Это **износ, которого нет**, и
**данные, которые никто не читает**.

## 2. Контекст и проблемы кода

### 2.1. Износа не существует ни в одной форме

Колонка `durability` есть в схеме `items.csv` (позиция 12 из 42). Проверка
читателей даёт три попадания, и все три — **комментарии о том, что читателя нет**:

```
src/game/item_table.h:19  //   durability (17 items)       no wear system
src/game/ranged_table.h:30 //   durability  zero on every ranged row. Firearms never wear.
src/game/weapon_table.h:33 std::uint16_t durability;  // 6  0 = never wears
```

То есть: 17 предметов несут значение прочности, **все** огнестрельные строки несут
ноль, и ни одна система не уменьшает это число. Заклинивания от грязи, засорения
фильтров и износа инструмента в дереве нет — ни как заглушки, ни как мёртвого кода.

Это чистый случай §35: данные авторы написали, кода нет. Отличие от прочих случаев
§35 в том, что здесь **нет даже читателя-заглушки** — терм не «всегда ноль», его
просто не существует.

### 2.2. Слотов экипировки нет; оружие выбирается автоматически

[ARCHITECTURE.md](../../ARCHITECTURE.md) таблица конфликтов, строка «Инвентарь
8×8 + слоты»: `kInvSlots = 64 = 8×8` ✓, но **слотов экипировки нет**. `equipSlot`
читается в одном месте и только сравнивается с `Armor` (`combat.cpp:724`); оружие
выбирается автоматически по лучшему стату (`ranged_pick.cpp:6`); `Tool` не
проверяет никто.

Следствие для износа: **некуда девать изношенный предмет**. Если фонарик сел, а
слота инструмента нет, игрок этого не заметит.

### 2.3. `stack_max` соблюдают три пути из пяти, и ломают в разные стороны

[problems.md](../../problems.md) §39 — ЖИВА. Два оставшихся пути ломают предел в
**противоположные** стороны, что хуже одностороннего дефекта: тест на «не больше
предела» пройдёт на одном пути и не заметит другой.

В схеме при этом две колонки — `stack_max` и `stack_declared`. Расхождение между
ними никем не проверяется.

### 2.4. Крафт: станки есть, износа инструмента нет

`craft.cpp:101-125` — `craft_station_ok(want, at)`, асимметричная проверка станка
(верстак умеет то, что умеют руки, но не наоборот). 24 рецепта в
`craft_recipes.csv`. Девять `craft_*` колонок в `items.csv` (механика,
электроника, расходники, био, химия, металл, кибернетика, псиматерия,
метаматерия) + `craft_station` + `craft_tier`.

Механизм есть. Отсутствует: **потребление ресурса станка** и **инструмент как
расходуемый предмет**. Сегодня верстак — это булев факт «я рядом», а не объект с
состоянием.

### 2.5. Экономика: 442 предмета с ценой, и `xp_for_quest` без вызовов

`economy.cpp` + `economy.csv` дают ценовые полосы. Но
[ARCHITECTURE.md](../../ARCHITECTURE.md) фиксирует: квесты и контракты платят
**только деньгами**, при том что манифест §5 требует XP за квесты, а
`xp_for_quest` (`rpg.cpp:300`) **не имеет ни одного вызова вне тестов**.

## 2a. Поправка: крафт построен существеннее, чем сказано в §2.4

Проверка `craft.h` даёт другую картину, чем «станки есть, износа нет»:

| Механизм | Значение | Строка |
|---|---|---|
| Рецептов | **442** — по одному на предмет, `kCraftRecipeCount == kItemCount` | craft.h:160 |
| Материалов | **9** | craft.h:101 |
| Тиров | 4 | craft.h:132 |
| Источников рецептов | 24 (1 базовый + 23 портированных) | craft.h:197 |
| Известность | битовое поле, 7 слов по 64 бита | craft.h:225 |
| Флаги | `kCraftKnownByDefault`, `kCraftDiscoverable` | craft.h:155-156 |
| Потолок материала | 999 999 | craft.h:229 |

**Рецепт N — это предмет N.** Решение сильное: не нужна ни таблица соответствия,
ни поиск, а «можно ли скрафтить предмет X» — это один битовый тест. Обратная
сторона: 442 рецепта означает, что большинство — заглушки, и **их наполнение
и есть работа**, а не постройка системы.

Тогда настоящая дыра §2.4 звучит уже: не «крафта нет», а **«у крафта нет
стоимости»**. Ни станок, ни инструмент ничего не теряют. Крафт — это проверка
битов и вычитание материалов; ничто не изнашивается, ничто не ломается,
ничто не кончается кроме самих материалов.

## 2b. Нужды: пять полей, пять зубов, и один провал

Сверено с `npc_pool.h:161-173` и `needs.cpp`.

```cpp
struct Needs {          // npc_pool.h:161, ровно 36 байт (static_assert)
    float food, water, sleep;      // резервы: убывают
    float pee, poo;                // давления: растут ТОЛЬКО из очереди
    float pendingPee, pendingPoo;  // съеденное, ещё не переваренное
    float hpDebt;                  // дробная убыль HP между тиками
    std::uint8_t seeded;
};
```

### 2b.1. Каждая нужда имеет зуб — ни одна не декоративна

| Нужда | Скорость | При отказе HP/с | Скорость хода | Интент |
|---|---|---|---|---|
| food | 0.08/с | **0.3** | ×0.75 | `IntentEat` |
| water | 0.12/с | **0.5** | ×0.65 | `IntentDrink` |
| sleep | 0.05/с | **0** намеренно | **×0.5** | `IntentSleep` |
| pee | 0.10/с | 0.1 | нет | `IntentToilet` |
| poo | 0.06/с | 0.1 | нет | `IntentToilet` |

Сумма ровно `1.0 HP/с` при всех четырёх отказах — заявлено в `needs.h:99-101` и
сходится.

**Три решения, которые надо сохранить:**

1. **Сон не отнимает HP.** Только скорость, и **порог `sleep < 10`, а не 0** —
   зуб срабатывает до опустошения полосы.
2. **Урон идёт по `kAttritionChannel`**, который на единицу выше последнего
   реального канала (`needs.h:200-201`). Проверка `if (i < kDamageChannels)` в
   `apply_damage` его пропускает, поэтому **броня не спасает от голода**. Это
   намеренно и правильно.
3. **`hpDebt` копит дробь.** Без него 0.1 HP/с при 125 Гц усекалось бы в ноль
   вечно — классическая ошибка, которой здесь избежали.

### 2b.2. Пищеварение замкнуто и доказано устойчивым

Давления **не растут сами** (`needs.cpp:30-38`): `digest()` переливает из
`pendingPee`/`pendingPoo`, а те наполняются только едой. **NPC, который никогда
не ел, никогда не хочет в туалет.** Это то, что делает петлю кухня→туалет→кухня
физичной, а не таймерной.

`needs.h:167-170` статически утверждает, что скорость переваривания превышает
приток в установившемся режиме — то есть **вечный долг невозможен**. Запас по
кишечнику всего 7 %, и это стоит знать при любой правке ставок.

### 2b.3. Провал: туалета не существует как объекта

Единственный путь облегчения — «физиологический запасной вариант» на клавише
взаимодействия (`main.cpp:3724-3729`), и он передаёт `100.0f, 100.0f` —
**полное облегчение в любой точке этажа**, минуя авторские частичные
`kToiletPeeRelief`/`kToiletPooRelief` (70/65).

Оставляет пятно и **не стоит ничего**. Значит вся цепочка «давление → интент →
поход в `Bathroom` → мебель `kPropToiletPan`» обходится одной кнопкой.

### 2b.4. Холодные NPC не имеют нужд вовсе

`needs_step` фильтрует по слою (`needs.cpp:270`): только воплощённые тела на
активном этаже. Проверка `macro_sim.cpp` и `population.cpp` на `Needs` —
пусто. `needs.h:42-44` заявляет намерение (макросим владеет холодными 950k),
но **грубые часы не реализованы**: нужды холодных просто заморожены.

**Следствие для ролей** ([спека 01](01_ALIFE_AND_UTILITY_AI.md)): Мародёр,
ушедший с активного этажа, не голодает. Роль, определённая через нужды,
существует только на одном этаже из 255.

### 2b.5. Шум от массы: подключён, но только для игрока

`main.cpp:3370-3374` — база 6 м × `noiseMult`, публикуется каждые 28 тиков при
боковой скорости² > 0.5, с вычетом вертикали через вектор гравитации слоя
(падение не считается шагами).

Но `noiseMult` берётся из `EncumbranceTick::playerEffect`, который заполняется
**только под `if (camera)`** (`encumbrance.cpp:94-98`). **NPC не публикуют шаги
вообще.** `noise.h:90` до сих пор помечает `Footstep` как «reserved; nothing
publishes this yet» — для игрока это уже неверно, для толпы всё ещё верно.

Прямое следствие для Дежурного из [спеки 01](01_ALIFE_AND_UTILITY_AI.md) §3a.2:
он не может услышать Мародёра, потому что Мародёр беззвучен.

### 2b.6. Выносливости нет и не должно быть

Отдельного ресурса нет. Перегруз уходит в **существующую** полосу сна
(`encumbrance.cpp:81-84`), и `encumbrance.h:33-36` объясняет почему: одна
усталость, а не две. Это верное решение, и вводить стамину значит его отменить.

## 3. Проектируемые структуры

### 3.1. Износ как ОДНА колонка состояния, а не как система на предмет

Ключевое проектное решение: износ обязан быть **свойством экземпляра в
инвентаре**, а не нового типа сущности. Инвентарь — 8×8 инлайновых слотов в строке
пула ([npc_pool.h](../../src/game/npc_pool.h)), и добавлять туда указатель на
объект состояния значит убить SoA.

```cpp
// src/game/inventory.h — РАСШИРЕНИЕ существующего слота.
//
// Слот сегодня несёт (itemId, count). Состояние добавляется ТРЕТЬИМ узким
// полем, а не отдельной таблицей: таблица потребовала бы ключа, ключ —
// аллокации, аллокация — того самого разреженного хранилища, которое
// performance.md запрещает по умолчанию.
struct InvSlot {
    std::uint16_t itemId = 0;
    std::uint16_t count = 0;
    // Состояние 0..255, где 255 = новое. ОДИН байт закрывает и износ оружия,
    // и заряд фонарика, и засор фильтра: это всегда «сколько ресурса осталось
    // в этом экземпляре». Разные СМЫСЛЫ различаются строкой предмета
    // (wear_kind), а не разными полями — иначе слот растёт под каждый новый
    // расходник.
    std::uint8_t condition = 255;
    std::uint8_t pad_ = 0;
};
static_assert(sizeof(InvSlot) == 6, "инвентарь 8x8 = 384 Б на тело");
```

**Почему 8 бит, а не 16.** 256 градаций износа — это 0.4 % на шаг, что мельче
любого игрового различия. 16 бит удвоили бы колонку инвентаря на 2²⁰ строк ради
незаметной точности.

### 3.2. Вид износа — строка таблицы предметов, не enum в коде

```cpp
// src/game/item_table.h — НОВАЯ колонка в ItemDef, генерируется из CSV.
enum class WearKind : std::uint8_t {
    None = 0,     // не изнашивается никогда (хлам, еда, документы)
    Durability,   // ломается от применения: оружие ближнего боя, инструмент
    Charge,       // тратится за использование: батарея фонарика, аптечка
    Fouling,      // ЗАСОРЯЕТСЯ ОТ СРЕДЫ, а не от применения: фильтр, респиратор
    Jamming,      // грязь копится -> растёт шанс осечки: огнестрел
};
```

Три последних вида различаются **источником** убыли, и это принципиально:

| Вид | Что тратит | Где стоит хук |
|---|---|---|
| `Durability` | удар / выстрел | `combat.cpp` в точке применения |
| `Charge` | секунды работы | `needs_step`-подобная развёртка |
| `Fouling` | **поле среды** (пыль, дым, газ) | шаг поля — спека 02 |
| `Jamming` | выстрел × грязь среды | обе точки |

`Fouling` — это то, что связывает направление 3 с направлением 2: **фильтр
засоряется от поля дыма/газа**, которого сегодня нет. Без спеки 02 фильтры
неотличимы от `Durability`.

### 3.3. Слоты экипировки — закрытие §2.2

```cpp
// src/game/equip.h — НОВЫЙ ФАЙЛ.
// Манифест §5 называет четыре слота. Enum — ordinal-индекс в массив,
// та же форма, что у RoomBit и IntentId.
enum class EquipSlot : std::uint8_t {
    Weapon = 0, Armor, Psi, Tool, kEquipSlotCount
};

// Экипировка — компонент ВОПЛОЩЁННОГО тела, а не строка пула: снаряжение
// снимается и надевается в бою, и переживать лифт ему не нужно — предметы
// и так лежат в инвентаре пула, здесь только ССЫЛКИ на слоты инвентаря.
struct Equipped {
    std::uint8_t invSlot[static_cast<std::size_t>(EquipSlot::kEquipSlotCount)];
    // 0xFF = пусто. Индекс в 64-слотовый инвентарь, поэтому 6 бит хватает,
    // а байт берётся ради выравнивания и читаемости.
};
static_assert(sizeof(Equipped) == 4);
```

Это одновременно чинит `ranged_pick.cpp`: оружие перестаёт выбираться
автоматически «по лучшему стату» и становится **решением игрока**, которое
можно проиграть, если ствол заклинило.

## 4. Алгоритмы и псевдокод

### 4.1. Заклинивание: вероятность, а не порог

Форма намеренно та же, что у карвинга (`carve_roll` в
[destruct.cpp:237](../../src/world/destruct.cpp)) — вероятностный ролл по
детерминированному хэшу, без хранимого RNG:

```
fire_weapon(shooter, slot, tick):
    def = item_def(slot.itemId)
    if def.wear == Jamming:
        # Грязь = 255 - condition. Среда добавляет к ней НАПРЯМУЮ,
        # поэтому запылённый этаж заклинивает стволы сам по себе.
        fouling = (255 - slot.condition) + env_dust_at(cell) * kDustToFouling
        # rand01(hash3(id, tick, salt)) — тот же примитив, что у всего дерева.
        if rand01(hash3(shooterId, tick, kJamSalt)) < fouling * kJamPerFouling:
            emit(JamEvent)            # событие в СУЩЕСТВУЮЩУЮ шину events.h
            return NoShot
    slot.condition = sub_sat(slot.condition, def.wearPerUse)
    ...
```

**Почему через шину событий.** `events.h` уже есть и уже развязывает системы.
Заклинивание должно быть слышно (звук), видно (HUD) и памятно (`MemHurt`-подобный
факт) — три потребителя, ни одного прямого вызова.

### 4.2. Засорение фильтра — читает поле, а не таймер

```
fouling_step(reg, pool, layer, gasField, smokeField, dt, tick):
    # Стаггер 1-из-N по идентичности — ровно как encumbrance_step,
    # по тому же аргументу: состояние меняется медленно, ответ почти
    # всегда вчерашний.
    for each body where (tick + id) % kFoulPeriod == 0:
        eq = reg.try_get<Equipped>(body)
        s = eq.invSlot[Tool]; if s == 0xFF: continue
        def = item_def(inv[s].itemId)
        if def.wear != Fouling: continue

        cell = wrap_macro(pos / kCellSize)
        load = gasField.at(cell) + smokeField.at(cell) * kSmokeFoulMult
        inv[s].condition = sub_sat(inv[s].condition,
                                   quantize(load * dt * kFoulRate))

        # ЧЕСТНОЕ ПОСЛЕДСТВИЕ: забитый фильтр перестаёт защищать,
        # и урон от газа идёт по тому же hazard-пути, что уже есть.
        if inv[s].condition == 0:
            emit(FilterDeadEvent)
```

### 4.3. Крафт из подручного мусора — рецепт по ТЕГАМ, а не по id

Мандат просит «сборку из подручного мусора». Сегодня рецепт называет конкретные
`recipe_items`. Мусорный крафт требует другого ключа — **тега**, и он уже есть:
`items.csv` несёт `tag_count`, `tags_hot`, `tags_all`.

```
craft_from_junk(inventory, station, recipe):
    # Рецепт мусорного класса требует НЕ предмет, а СВОЙСТВО:
    # «две любые вещи с тегом Metal и одна с тегом Cloth».
    for each requirement (tagMask, count) in recipe.tagReqs:
        found = 0
        # Порядок обхода инвентаря детерминирован (слоты 0..63),
        # поэтому результат воспроизводим без хранимого состояния.
        for slot in 0..63:
            if item_def(inv[slot].itemId).tags & tagMask:
                take = min(count - found, inv[slot].count)
                # ДЕШЁВОЕ ТРАТИТСЯ ПЕРВЫМ: сортировки нет, есть
                # предпочтение по value_rub при равенстве тегов.
                found += take
        if found < count: return Fail
```

Это одна новая структура (`tagReqs`) и ноль новых механизмов: теги, значения и
станки уже в CSV.

## 5. Критерии приёмки

### 5.1. Износ

- [ ] `suite_wear.inl`: для каждого `WearKind` — предмет теряет состояние от
      своего источника и **не теряет** от чужого. Фильтр не изнашивается от

## 6. Порядок работ

```
A. Гейт §35 на колонки CSV           <- ловит durability и всё будущее
B. InvSlot.condition + WearKind      <- одна колонка, одна enum-строка
C. EquipSlot / Equipped              <- нужен, иначе износ невидим
D. Durability + Charge               <- не зависят от полей среды
E. Сейв v10 + round-trip             <- обязателен до любого релиза с B/C
F. Jamming                           <- зависит от D
G. Fouling                           <- ЗАВИСИТ ОТ СПЕКИ 02 (поля дыма/газа)
H. Крафт по тегам                    <- независим, можно параллельно
I. xp_for_quest wiring               <- одна строка, независим
```

**G — единственная реальная межспековая зависимость.** Фильтр без поля дыма — это
таймер, переодетый в фильтр; такую подделку [AGENTS.md](../../AGENTS.md) §Честность
симуляции запрещает прямо.

## 7. Явные не-цели

- **Не переписывать `mass_g`.** Он приземлился правильно и с аргументом.
  Единственная допустимая правка — перенос ёмкости со Силы на Выносливость,
  и только когда слот 5 атрибутов появится ([README.md](../../README.md) §5
  уже помечает это как одну строку).
- **Не вводить деградацию предмета в мире.** Износ — свойство экземпляра в
  инвентаре; предмет, лежащий на полу, не ржавеет. Иначе нужен тик по всем
  контейнерам этажа, а это O(предметы), не O(тела).
- **Не делать ремонт до износа.** Ремонт без износа — механика без задачи.
