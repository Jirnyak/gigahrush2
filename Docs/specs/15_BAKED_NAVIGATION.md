## 3. Корень: испечено поле ПОЛЁТА, а потребителю нужно поле ХОДЬБЫ

Это главный вывод документа, и он объясняет всё остальное.

```cpp
// nav.cpp:17-19 — единственный предикат проходимости
bool blocked(const MacroGrid& g, int x, int y, int z) {
    return g.mask(x, y, z).full();
}
```

Ни теста опоры, ни высоты шага, ни просвета над головой. BFS симметричен по шести
соседям (`nav.cpp:62-66`, `110-113`): `+z` и `−z` равноправны с `±x/±y`.

**Следствие: поле маршрутизирует сквозь открытый воздух так же свободно, как по
полу.** Это поле полёта. Тело ходячее им пользоваться не может — и именно поэтому
потребитель обязан выбрасывать вертикальные шаги:

```cpp
// wander.cpp:387-388
const bool horizontalStep = (flow < 6) && (nav::kNavDir[flow][2] == 0);
```

Цена отброса зафиксирована в самом коде (`wander.cpp:400-404`): **110 из 120
жителей нижнего этажа получают вертикальный первый шаг.** То есть ~92 % тел
игнорируют 128 МиБ на первом же шаге и идут по прямому пеленгу на колонну узла
(`wander.cpp:410-431`). `ai.cpp:886-903` делает то же самое для комнатных
маршрутов.

**Это не баг потребителя.** Потребитель поступает единственно возможным образом с
полем, которое ему дали. Дефект — в предикате `blocked`, и починка меняет
**печение**, а не читателя.

### 3.1. Предикат опоры

```cpp
// ЗАКОН: gravity is a vector. Опора — это клетка НАПРОТИВ направления гравитации,
// а не «z-1». Идиома уже есть в дереве: regime_down (container.cpp:294).
//
// СТОИМОСТЬ: один дополнительный mask()-запрос на соседа в BFS. Печение уже
// 3,7 с; это добавит ~25 % к обходу, но сократит поле до проходимого множества,
// то есть УМЕНЬШИТ фронт BFS. Замерить, а не предполагать.
bool walkable(const MacroGrid& g, ivec3 c, ivec3 down) {
    if (g.mask(c.x, c.y, c.z).full()) return false;          // сама клетка занята
    const ivec3 s = wrap_cell(c + down);                      // клетка опоры
    return g.mask(s.x, s.y, s.z).any();                       // есть на что встать
}
```

`any()`, не `full()`: встать можно на частично выеденную клетку. Это единственное
место, где суб-воксельная маска обязана участвовать в навигации — не для
геометрии пути, а для теста опоры.

### 3.2. Что тогда делать с вертикальными переходами

Убрав полёт, мы теряем связность между этажами внутри этажа. Её надо вернуть
явно, а не через симметричный BFS:

| Переход | Как выразить |
|---|---|
| Лестница / трап | клетка с флагом `Climbable`: рёбра `±z` разрешены только на ней |
| Лифтовая шахта | ребро решётки между узлами, а не клеточное ребро |
| Падение | разрешено всегда в направлении гравитации, необратимо |

Последняя строка важна: **падение — ребро односторонее.** BFS по шести соседям
делает его двусторонним, то есть считает, что тело может подняться туда, откуда
упало. Это второй источник непроходимых маршрутов, независимый от первого.

## 4. Печение: 3,7 с, и это не «несколько сотен мс»

Единой функции полного печения нет — оба вызывающих собирают её из двух половин
(`nav_async.cpp:39-41`, `floor_stream.cpp:362-363`).

- Параллельно: `parallel_for(kNodes, ...)` в `nav.cpp:172` (грубая часть) и
  `nav.cpp:212` (тонкая). При `threads=0` берутся все потоки, предел `n=64`
  (`jobs.h:34-37`), разбиение непрерывными куска́ми `chunk=(n+t-1)/t` (`jobs.h:44`).
- **Однопоточно намеренно:** Флойд–Уоршелл (`nav.cpp:176-202`) и `bake_nearest`
  (`nav.cpp:133`), комментарий `nav.cpp:132` — *«Single-threaded ⇒ bit-identical»*.
  Это верное решение: воспроизводимость важнее секунды, потому что кэш
  сериализуется и должен совпадать побайтово.
- **Замер, цитата из `nav_async.h:6-7`:** *«Measured on a 20-thread machine: coarse
  ~1.9 s + fine ~1.8 s, so every elevator ride cost a ~3.7 s frozen frame.»*

`nav.md:127` говорит «несколько сотен миллисекунд». Расхождение **на порядок**, и
в сторону, которая ломает проектирование: 3,7 с — это не хитч, это загрузочный
экран, и лифт обязан быть спроектирован вокруг этого числа.

## 5. Локальное перепекание: было, удалено, и удалено правильно

`nav.h:124-135` фиксирует удаление `LazyFieldRebaker` (2026-08-06). В `src/` и
`tests/` не осталось ни одного упоминания.

Причина в коде названа точно и заслуживает сохранения: `flow[node]` — это BFS
**из** узла по всему 128³, поэтому карв в любом месте инвалидирует **все 64
поля**, тогда как перепекатель ставил в очередь ровно одно. Цитата: *«a racy 1/64
fix is worse than the honest debt»*.

**Гранулярность инвалидации сегодня: весь этаж, все 64 поля, только на границе
печения** (загрузка этажа / после самосбора).

**Следствие, которое надо назвать вслух: разрушаемость молча деградирует
навигацию.** Игрок пробивает стену — толпа не узнает об этом до следующей загрузки
этажа. Обратное тоже верно и хуже: самосбор заваливает коридор, а поле продолжает
маршрутизировать через него, и тела идут в тупик.

Правильное решение — не возвращать перепекатель, а **инвертировать поле**: если
хранить не «направление от каждого узла», а «расстояние до каждого узла», карв
меняет локальную окрестность, и починка становится локальной по построению. Это
переписывание печения, а не заплатка, и в фазу 3 оно не влезет.

## 7. Закон гравитации: печение чисто, потребители нет

**Нарушений в `nav.h`/`nav.cpp` нет.** Ни жёсткого `−Z`, ни `z+1`, ни константы
высоты шага. `kNavDir` (`nav.h:77-79`) лишь **упорядочивает** оси, ставя z
последней, — это порядок перечисления, а не предположение о направлении.

Нарушение живёт в слое, который ест байт потока, и оно **явное, задокументированное
и одинаковое в трёх местах**:

| Место | Что сказано |
|---|---|
| `ai.cpp:862-863` | *«kNavDir 0..3 are ±x/±y; 4..5 are the gravity axis»* |
| `wander.cpp:387-388` | фильтр по `kNavDir[flow][2] == 0` |
| `wander.cpp:443` | *«z is left to gravity: this is locomotion, not flight»* |
| `ai.h:669`, `ai.h:943` | *«v.z belongs to gravity»* |
| `wander.cpp:411-412` | цель строится из `ix`/`iy`; `iz` отброшен |

Ни один из них не спрашивает `GravityRegime`, хотя правильная идиома в дереве
есть и применяется: `regime_down(world.gravity().regime)` (`container.cpp:294`), а
`combat.h:478` цитирует закон дословно и протаскивает `const GravityField*`
(`combat.h:485`).

**Под режимом Sideways или Zero потребители отфильтруют не ту ось.** Толпа либо
замрёт, либо пойдёт боком в стену. Это не гипотеза: `kNavDir[flow][2]` — жёсткий
индекс 2 в массиве направлений, и при боковой гравитации «горизонтальным» станет
именно тот шаг, который надо отбросить.

Формулировка для приёмки: **фильтр обязан спрашивать `regime_down`, а не индекс
2.** Одна строка, и она снимает нарушение в трёх местах сразу.

## 11. Явные не-цели

- **Не возвращать `LazyFieldRebaker`.** Причина удаления (`nav.h:124-135`) верна:
  один карв инвалидирует все 64 поля, очередь на одно — гонка. Возврат заплатки
  вернёт и гонку.
- **Не печь `FineNav` в стриминге этажей.** `floor_stream.cpp:348-351` уже
  объяснил, чем это кончилось: 130 МиБ и многосекундный стопор, освобождённые
  непрочитанными.
- **Не делать Флойда–Уоршелла и `bake_nearest` многопоточными.** Побитовая
  идентичность нужна сериализуемому кэшу; секунда дешевле расхождения кэша между
  прогонами.
- **Не хранить `FineNav` в сейве.** Выводимо из геометрии — та же причина, по
  которой [спека 10](10_SAVE_AND_PERSISTENCE.md) §3 держит его вне блоба.
- **Не убирать фильтр горизонтальности до починки предиката.** Он сегодня
  единственное, что мешает толпе летать. Снять его раньше `walkable` — значит
  выпустить ходячие тела в поле полёта.
