## 0. Поправка: CI существует

Я исходил из того, что все гейты локальные и зависят от человека, который их
запустит. **Это неверно** — в репозитории шесть workflow, из них один сборочный:
`cmake-multi-platform.yml`, на push и PR в `main`, матрица
`ubuntu-latest` (gcc, clang) + `windows-latest` (cl), Release, затем `ctest`.

Но проверка того, **может** ли он выполниться, даёт ответ хуже, чем его
отсутствие.

## 1. Конвейер обязан падать на конфигурации — ЗАКРЫТО 2026-08-12

> Принят **второй вариант** из таблицы ниже, ровно как и рекомендовала спека.
> `cmake-multi-platform.yml` заменён на `source-rules.yml`: один шаг,
> `cmake -P tools/check_source_rules.cmake`, без единого шага установки — потому
> что ему нечего устанавливать.
>
> **Проверено, а не заявлено:** та же команда прогнана на чистом `git archive`
> дерева, без Vulkan, без SDL3, без сборки — `GIGA_SOURCE_RULES=PASS
> files_scanned=245`, код возврата 0. Именно этой проверки не хватало прежнему
> файлу: он был вставлен шаблоном и никем не запущен.
>
> Значок README (§6.1, пункт 0.2б роадмапа) заменён в том же коммите на
> настоящий значок Actions этого workflow. Оба конца ложного сигнала снимаются
> вместе: конвейер, который не мог запуститься, и картинка, утверждавшая, что он
> зелёный.
>
> **Пункт 0.4 роадмапа (`ctest --output-on-failure` в CI) этим ОТМЕНЁН, а не
> выполнен:** `ctest` в конвейере больше нет, потому что без SDK его не бывает.
> Он вернётся вместе с первым вариантом — провижнингом Vulkan SDK и SDL3, — и
> тогда флаг понадобится снова.
>
> Первый вариант сознательно не сделан: он требует провижнинга на каждый раннер,
> и добавить его непроверенным значило бы воспроизвести ровно ту ошибку, которую
> этот коммит убирает — конвейер, объявленный рабочим тем, кто ни разу не видел
> его прогона.

Ниже — исходный разбор.

Между `actions/checkout@v7` (`:48`) и `Configure CMake` (`:57`) **нет ни одного
шага установки зависимостей**. Проверено построчно: `checkout` → «Set reusable
strings» (вычисление пути сборки) → `Configure CMake` → `Build` → `Test`.

При этом `CMakeLists.txt` требует:

```cmake
find_package(Vulkan REQUIRED)     # :167
# и FATAL_ERROR, если не найден glslc  :168-171
```

На голом GitHub-раннере нет ни Vulkan SDK, ни `glslc`, ни SDL3. **Конфигурация
не может завершиться успешно ни на одной из трёх ног.**

Это шаблон GitHub «CMake on multiple platforms», добавленный без правок:
комментарий-заголовок стартового шаблона на месте, описание матрицы про «3
configurations» тоже.

**Почему это хуже отсутствия CI.** Значок «Build: Passing» стоит в README
(`:7`). Отсутствие конвейера честно; конвейер, который никогда не был зелёным,
плюс значок, утверждающий обратное, — это ложный сигнал в самом видном месте.

**Дешёвая честная починка** — одна из двух, и выбор за владельцем:

| Вариант | Цена | Что даёт |
|---|---|---|
| Добавить установку Vulkan SDK + SDL3 в матрицу | час-два | настоящий кросс-платформенный гейт |
| Свести CI к тому, что **работает без SDK**: `source_rules` (это `cmake -P`, ему ничего не нужно) | 15 минут | зелёный сигнал, которому можно верить |

**Рекомендация — второй.** `source_rules` не требует ни Vulkan, ни SDL3, ни
компилятора: это скрипт `cmake -P` над текстом. Он единственный гейт, который
сегодня можно сделать зелёным честно, и он же — тот, что ловит нарушения правил
исходников. Начать с малого работающего гейта лучше, чем с большого мнимого.

### 1.1. macOS не в матрице

`AGENTS.md:216` называет macOS «primary, and the mechanical enforcer of the
no-throw rule». **Именно этой платформы в матрице нет** (`:26`).

Смягчающее обстоятельство: ноги Ubuntu получают `-fno-exceptions`
(`CMakeLists.txt:105`), то есть правило механически покрыто — **если** эти ноги
вообще выполняются. С учётом §1 не выполняются.

### 1.2. `ctest` без `--output-on-failure`

Workflow (`:75`) запускает голый `ctest`. `AGENTS.md:222` предписывает
`--output-on-failure`.

Расхождение неприятнее, чем кажется, потому что **все четыре теста висят на
`PASS_REGULAR_EXPRESSION`**. Провал сообщает лишь «регулярка не совпала» и
**скрывает саму строку со счётчиком**, то есть именно то число, ради которого пин
и написан. Диагностика вырезана ровно там, где она единственно полезна.

## 2. Асимметрия платформ: пять различий, меняющих поведение

Не синтаксические, а поведенческие. Каждое означает, что «зелено на Windows» и
«зелено на macOS» — разные утверждения.

| Различие | MSVC | Clang/GCC | Последствие |
|---|---|---|---|
| Исключения | `/EHsc` **всегда** | `-fno-exceptions` при `rtti==OFF` | правило no-throw механически не проверяется на Windows |
| Уровень оптимизации | умолчание CMake | явные `-O3` / `-O2` | **хосты не сравнимы по производительности** |
| LTO | **никогда** — `check_ipo_supported` вызывается только под `if(NOT MSVC)` (`:78-80`) | Release и RelWithDebInfo | цифра «5,9 мс при `-O3 -flto`» на Windows невоспроизводима |
| UBSan | **нет** — только `/fsanitize=address` (`:68`) | `-fsanitize=address,undefined` (`:50-52`) | опция названа «Address + UB», на Windows даёт половину **молча** |
| Предупреждения CRT | `_CRT_SECURE_NO_WARNINGS` (`:66`) | нет аналога | класс диагностик выключен на одном хосте |

Третья строка — самая тихая и самая дорогая. `AGENTS.md:239-240` приводит
5,9 мс как базовую цифру Release. На Windows LTO нет вовсе, значит эталонное
число измерено на конфигурации, которая на этой машине **не собирается**. Любое
сравнение «стало медленнее» между хостами бессмысленно, пока это не выровнено.

Четвёртая — ловушка ожидания: разработчик включает `GIGA_ASAN=ON`, читает
описание «Address + UB sanitizers» и считает, что проверил UB. На Windows не
проверил. Опция обязана либо ставить UBSan, либо **печатать, что не ставит**.

## 3. Что сделано правильно и переделывать не надо

Отдельный раздел, чтобы правки не сломали удачное.

**Все четыре `GLOB_RECURSE` несут `CONFIGURE_DEPENDS`** (`:206-207`, `:219`,
`:354`, `:355-356`). Классической ловушки «добавил файл — cmake не перезапустился»
здесь нет. Шесть глобов в `check_source_rules.cmake` без него безвредны: скрипт
исполняется через `cmake -P` и переглобит при каждом запуске, графа сборки у него
нет.

**Ни одна зависимость не висит на ветке.** EnTT `v3.14.0`, ImGui `v1.91.5`,
libktx `v4.4.0`, SDL3 `release-3.4.12` — все на тегах релизов. Это доверие к тегу,
а не адресация по содержимому, но «плавающего `main`» нет нигде.

**Компиляция шейдеров вшита в граф правильно:** 18 выходов SPIR-V,
`add_custom_target(giga_shaders)` (`:348`), `add_dependencies` (`:367`). Правка
стадии вызывает пересборку.

**Ни одного захардкоженного абсолютного пути и ни одной прибитой версии SDK.**
Все пути выведены из `CMAKE_SOURCE_DIR`/`CMAKE_BINARY_DIR`.

**Подавлено ровно одно предупреждение на компилятор**, и это один и тот же класс:
`/wd4100` и `-Wno-unused-parameter`. Сужение (`C4244`/`C4267`), `-Wsign-compare` и
`-Wunused-result` **не** подавлены — для движка на сырой индексной арифметике это
верный выбор.

## 4. Три реальные дыры сверх CI

### 4.1. Зависимость шейдеров от `#include` неполна

Список включаемых `.glsl` (`:235`) — **ручная пара**, и она передаётся только
четырём командам из восемнадцати (`:242`, `:303`, `:332`, `:344`). Шесть
`.comp`-шейдеров её не получают (`:253`, `:263`, `:273`, `:283`, `:293`).

Сегодня это корректно ровно до тех пор, пока ни один вычислительный шейдер не
включает `material_surface.glsl` или `volumetric_fog.glsl`. **Но третий
`.glsl`-инклюд, добавленный завтра, будет невидим для всех восемнадцати
зависимостей** — вернётся ровно тот отказ «нечего делать, .spv устарел», который
комментарий на `:229-234` описывает как уже случившийся.

Починка: собирать список инклюдов глобом, а не рукой, и передавать всем командам.

### 4.2. TSan отсутствует, а гонки в проекте уже были

ASan и UBSan есть (`:44`, `:50-52`). **TSan нет нигде**, опции `GIGA_TSAN` не
существует.

При этом `src/core/jobs.h:175-176` разбрасывает 64 BFS по узлам на `std::thread`,
а удалённый `LazyFieldRebaker` был **настоящей гонкой, найденной чтением, а не
инструментом** (`nav.h:124-135`). То есть класс дефектов подтверждён на практике,
а инструмента для него нет.

Плюс: ASan не включается в CI никогда — матрица не выставляет `GIGA_ASAN`, — так
что обе конфигурации санитайзеров живы ровно настолько, насколько их последний раз
гонял человек.

### 4.3. `-Werror` нет ни на одном хосте

`AGENTS.md:256-260`: *«Ensure zero warnings… Treat warnings as errors in review»*.
Формулировка честная — и она же признаёт, что политика нулевых предупреждений
**держится ревьюером, а не сборкой**.

Для проекта, где закон гранулярности и закон гравитации проверяются гейтами,
это единственное правило, оставленное на человека без механической опоры.

## 5. Что `AGENTS.md` §Build утверждает вопреки `CMakeLists.txt`

| Утверждение | Реальность |
|---|---|
| `:239-240` «5,9 мс при `-O3 -flto`» как базовая Release | На Windows LTO **никогда** не включается (`:78-80`) |
| `:260-262` «шейдеры `*.vert\|frag` компилируются в SPIR-V» | Занижено: шесть `.comp` тоже, и три фрагментных компилируются **дважды** с разными `-D`. Читатель не ожидает существования `cube_tex.frag.spv` — а именно его отсутствие роняет `cube_pass.cpp` на инициализации |
| `:222` `ctest --output-on-failure` | CI запускает голый `ctest` (`workflow:75`) |
| `:216` macOS — механический страж правила no-throw | В матрице CI macOS нет |
| `:256-260` нулевые предупреждения | Ни `/WX`, ни `-Werror` |

Плюс умолчания: раздел не упоминает `GIGA_ASAN`, `GIGA_BUILD_TESTS`,
`ENTT_NOEXCEPTION` и libktx — всё это живёт в `CMakeLists.txt`. Список
зависимостей в шапке самого `CMakeLists.txt` (`:25-29`) тоже не называет libktx,
который этот же файл выкачивает сотней строк ниже.

## 6. Критерии приёмки

### 6.1. CI, которому можно верить

- [ ] Принято решение: **чинить матрицу** (установка Vulkan SDK + SDL3) либо
      **сузить** CI до `source_rules`. Третьего варианта — оставить как есть —
      нет, потому что README несёт значок «Build: Passing».
- [ ] Первый зелёный прогон существует и на него можно сослаться. До этого любое
      утверждение о состоянии CI — предположение.
- [ ] `ctest` получает `--output-on-failure`. Иначе провал скрывает счётчик,
      ради которого написан пин.
- [ ] Значок в README отражает **реальный** статус (badge из Actions), а не
      статичную картинку.

### 6.2. Выравнивание платформ

- [ ] MSVC получает явный уровень оптимизации, как и Clang. Сегодня хосты не
      сравнимы, и сравнение производительности между ними бессмысленно.
- [ ] Цифра «5,9 мс» помечена платформой, на которой измерена, **либо** LTO
      включается на MSVC.
- [ ] `GIGA_ASAN` на Windows либо ставит UBSan, либо **печатает**, что не ставит.
      Молчаливая половина хуже честного отказа.

### 6.3. Механика вместо ревью

- [ ] Список `.glsl`-инклюдов собирается глобом и передаётся **всем** командам
      компиляции шейдеров.
- [ ] Решение по `-Werror` принято письменно. Если нет — записано, почему нет.
- [ ] Опция `GIGA_TSAN` существует **или** записано решение, что гонки ловятся
      чтением. Прецедент есть (`nav.h:124-135`), и он это оправдывает.

## 7. Порядок работ

```
A. Решение по CI: чинить или сузить      <- владельца; блокирует B и C
B. Свести CI к source_rules              <- 15 минут, первый честный зелёный
C. ctest --output-on-failure             <- одна строка
D. Значок README из Actions              <- одна строка, снимает ложный сигнал
E. Явный уровень оптимизации на MSVC     <- выравнивает хосты
F. Глоб для .glsl-инклюдов               <- закрывает возврат старого отказа
G. Пометить или включить LTO             <- зависит от E
H. GIGA_TSAN                             <- отдельное решение, не срочно
```

**B, C, D — полчаса**, и после них сигнал «зелено» перестаёт врать. Это
предшествует всему остальному: гейт, которому не верят, не гейт.

## 8. Явные не-цели

- **Не переводить зависимости на SHA вместо тегов.** Теги релизов — разумный
  компромисс; переход на SHA удорожает обновления ради риска, который для четырёх
  известных библиотек невелик.
- **Не включать `-Werror` в шиппинг-сборке владельца одним движением.** Сначала
  нулевые предупреждения на обоих хостах, потом гейт. Обратный порядок
  заблокирует работу.
- **Не добавлять macOS в матрицу до §1.** Четвёртая нога сломанного конвейера —
  это четвёртый красный крест, а не покрытие.
- **Не трогать `CONFIGURE_DEPENDS` и теговые пины.** Это уже сделано правильно.
- **Не собирать Debug ради удобства.** 62,2 мс против 5,9 мс на кадр читается как
  регрессия последней правки и стоит часов поиска.
