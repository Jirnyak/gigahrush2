## 4. Контрплей — это ПОЛ урона, а не множитель

`combat.cpp:94-97`, внутри `apply_damage`, **до** брони и до множителя WallBrace.

`monster_traits.cpp:114-133`:

```
if vulnChannel == kNoVulnChannel or vulnFloorPct == 0:  return base
if vulnChannel != channel:                              return base
floorDmg = ceil(maxHp * pct / 100)
if pct >= 100:  floorDmg = maxHp + 1        # гарантированное убийство
return max(base, floorDmg)
```

**Порядок важен:** пол применяется **до** `mitigate`, поэтому поднятый пол затем
режется бронёй. Пол не финален.

| Вид | Пол | Канал |
|---|---|---|
| Борщевик | 44 % от maxHp | Fire |
| Кровавое растение | 38 % | Fire |
| Туманная акула | maxHp + 1 (убийство) | Fire |
| Рой | текущее HP (убийство) | Fire |

**Все четыре — огонь.**

### 4.1. Поправка к заголовку: он устарел

`monster_traits.h:101-103` утверждает, что контрплей «не может сработать в
работающей игре… ни один источник не производит `DamageChannel::Fire`».

**Это уже неверно:** `main.cpp:3430` передаёт `Fire`.

Но производитель — аура Спорового ковра, бьющая **по игроку**. Четыре
огнеуязвимых вида по-прежнему огня не получают. **Механика жива в коде и
недостижима на практике** — и это ровно тот класс, который статический поиск
объявит работающим.

Огонь из [спеки 02](02_VOXEL_PHYSICS_AND_FLUIDS.md) §4a закрывает это по
построению: поле жара наносит `Fire` всему, что в клетке.

## 5. Спавн: глубина фильтрует, но не взвешивает

`spawn_floor_mobs` (`mob_spawn.cpp:234+`), конвейер:

1. Численность `mob_count_for_floor(floorNumber, danger, theme)`, обрезка по `cap`
2. Уровень `mob_level_for_floor` — **один на весь этаж**
3. Построение ростера: один проход по 68 строкам, фильтр `floorMask & floorBit`,
   пропуск при `spawnWeightX10 == 0`, раскладка по ростерам комнат
4. Взвешенный выбор **на комнату** (`mob_spawn.cpp:336-343`)
5. Размер стаи из `packMode/packMin/packMax`

**Взвешен ли по глубине?** Косвенно и дискретно. Вес — плоский
`spawnWeightX10`, **одинаковый на любой глубине**. Глубина входит только как
(а) фильтр обитания через `anchor_for_floor`, снапящий к одному из шести якорей,
(б) численность, (в) уровень.

**Никакого пропорционального перевзвешивания нет: на данном якоре состав
идентичен на любом этаже.** `tier` не читается спавнером вовсе.

Второй, параллельный взвешенный выбор — туманный спавнер
(`mob_spawn.cpp:519-528`), дополнительно гейтится `minSamosbor`.

### 5.1. `kMobSpawnCap` — не то, чем кажется

`main.cpp:882`, значение **600**. Единственное использование — `main.cpp:1027`,
аргумент `cap` одного вызова `spawn_floor_mobs`.

Значит это **предел на этаж за один вызов, а не потолок живой популяции**. Ничто
его не декрементирует, и туманный спавн его **не сверяет**. Комментарий
`:878-881` называет его страховкой от насыщения бюджета 4096, а не живым лимитом.

## 6. Охота — ограничитель, а не система целеуказания

`hunt.h` моделирует хищничество монстров по толпе NPC. Четыре сдержки:

| Сдержка | Значение |
|---|---|
| Игрок важнее толпы | приоритет |
| `kHuntRadius` | 6.0 м против 20 м агро на игрока |
| `kHuntShare` | **32** — лицензирован один монстр из 32 |
| `kHuntEpochTicks` | 2400 — конечное окно |

Всё — чистые функции от `(id, тик)`. Ни хранимой цели, ни состояния.

**Подключено:** `combat.cpp:582` (`mob_hunts_npcs`), `combat.cpp:592`
(`nearest_prey`), оба внутри `mob_attack_step`. Полный набор вызовов — два.

### 6.1. Довод о размазывании урона

`hunt.h:39-42`:

> spreading damage over more bodies does not lower the death toll — it delays it,
> and leaves a floor of half-dead residents, because nothing heals a crowd body

**HP толпы монотонно убывает.** Регенерации NPC нет нигде, поэтому урон —
интеграл, а не скорость. Любая мера, перераспределяющая урон (бегство, разнообразие
целей, короткие окна), меняет **когда** тело умрёт, а не **умрёт ли**.

Хуже: `hunt.h:75-78` отмечает, что короткие окна **ускоряют** убыль — брошенное
полудобитое тело добивается следующей когортой вдвое быстрее.

Поэтому единственный работающий регулятор — **дефицит охотников**, что и делает
`kHuntShare = 32`. Подтверждено независимо в `faction_relations.h:204-208`, где
вражда фракций ставит пол урона на `hp-1` по той же причине.

**Это прямой довод за Санитара** из [спеки 01](01_ALIFE_AND_UTILITY_AI.md) §3a.3:
пока ничто не лечит толпу, любое расширение источников урона по ней —
односторонний счётчик. Санитар — не украшение, а предпосылка честного
дружественного огня.

## 8. Сложность решается один раз при спавне и замерзает

**Никакого рантайм-масштабирования по глубине нет.**

- Уровень считается **один раз на этаж**, не на моба и не на тик
  (`mob_spawn.cpp:242`, `:606`)
- `mob_level_for_floor` (`mob_table.cpp:955`):
  `max(danger, round(1 + depth01*8 + (danger-1)*0.55))`, зажат 1..12 — но
  `mob_table.h:275-278` фиксирует, что фактический потолок **11**, потому что
  зонного бонуса референса здесь нет
- HP масштабируется единожды при спавне (`mob_table.cpp:969`):
  `base * (1 + 0.12*(level-1))`
- **Урон не масштабируется уровнем вообще.** `MobDef::dmg` используется сырым.
  `hunt.h:70-73` показывает, что множитель предполагался («медианный урон 13 …
  ×1.24 для уровня 3»), но **такого множителя в дереве нет**

**Монстр уровня 11 бьёт ровно как уровня 1; вырос только пул HP.** Это
единственная содержательная дыра баланса, найденная в бестиарии.

## 9. Проектируемое

### 9.1. Урон должен масштабироваться уровнем — предполагалось и не сделано

```cpp
// mob_spawn.cpp, рядом с существующим масштабированием HP при спавне.
// Форма и коэффициент взяты из hunt.h:70-73, где множитель ОПИСАН
// как существующий. Ничего не изобретается — восстанавливается заявленное.
mr.dmg = static_cast<std::int16_t>(
    static_cast<float>(d.dmg) * (1.0f + kMobDmgPerLevel * (level - 1)));
```

При `kMobDmgPerLevel = 0.12` (тот же шаг, что у HP) уровень 11 даёт ×2.2 — что
согласуется с ×1.24 для уровня 3 из `hunt.h`.

### 9.2. Подключить `mass_g` монстров

```cpp
// mob_spawn.cpp, там же где ставится Transform/Velocity.
// Формула p = mv уже в дереве и применяется к предметам.
reg.emplace<Mass>(e, Mass{static_cast<float>(d.massG) * 0.001f});
```

Оживляет отбрасывание, урон от падения и импульс — три закона, уже написанных.

### 9.3. Перевзвешивание по глубине — данные, не код

```cpp
// Множитель веса спавна по глубине, СТРОКА НА ЯКОРЬ.
// Сегодня состав на якоре идентичен на любом этаже; это делает
// шесть якорей шестью статичными наборами.
inline constexpr std::uint8_t kAnchorDepthBias[kAnchorCount][kMobTierCount] = {
  /*            T0   T1   T2   T3 */
  /* anchor 0 */ { 100,  60,  20,   0 },
  /* anchor 5 */ {  10,  40, 100, 120 },
  // ...
};
```

Это оживляет `tier`, который спавнер сегодня не читает вовсе.

### 9.4. Шесть мёртвых аксессоров — следствие мёртвой воды

**Не подключать их отдельно.** Все шесть требуют мокрых клеток, которых нет.
Работа принадлежит [спеке 02](02_VOXEL_PHYSICS_AND_FLUIDS.md): оживить
жидкость — и шесть аксессоров, `TerrainPref`, регенерация и приманки оживают
вместе.

Записать это зависимостью, а не задачей бестиария.

## 11. Явные не-цели

- **Не авторировать все 68 строк черт.** Авторировано 21; строка по умолчанию с
  `authored = 0` — законный ответ для проходного вида.
- **Не превращать три захардкоженные способности в данные преждевременно.** Три
  `if` дешевле колонки CSV, которую прочитают трижды.
- **Не подключать шесть мёртвых аксессоров до оживления воды.** Они не мертвы —
  они ждут мира.
- **Не смягчать `kHuntShare`.** Единственный работающий регулятор смертности
  толпы, и `hunt.h` объясняет почему.
