Митигация урона тоже сделана правильно и **в одном месте**
(`combat.cpp:91`: *«Mitigation happens exactly once, here. Nothing downstream
sees `raw`»*):

```cpp
std::int16_t mitigate(std::int16_t raw, std::int8_t resistPct) {
    int r = resistPct;
    if (r > 95) r = 95;      // никогда не полный иммунитет
    if (r < -100) r = -100;  // отрицательный резист = уязвимость, не клампится в 0
    int out = raw - (raw * r) / 100;
    return out < 0 ? 0 : static_cast<std::int16_t>(out);
}
```

Порядок применения: уязвимость от черт → броня по каналу → множитель поведения
защитника, с полом в 1 при `dmg > 0`.

## 2. Дефекты

### 2.1. Манифест запрещает исключения для дружественного огня — в коде их пять

[ARCHITECTURE.md](../../ARCHITECTURE.md) §Манифест п.5: *«Снаряды — честная
баллистика в торе, никаких friendly-fire-исключений; граната скачет по вокселям,
осколки бьют и владельца»*.

Фактически (`combat.cpp:1115-1160`, `:1174`):

| # | Исключение | Строка | Обоснование в коде |
|---|---|---|---|
| 1 | Снаряд не бьёт владельца (игрок) | `combat.cpp:1121` | «he shoots himself the instant he fires» |
| 2 | Снаряд не бьёт владельца (моб) | `combat.cpp:1145` | выстрел рождается в 0.6 м, радиус 0.75 м |
| 3 | Выстрел игрока (`team == 1`) бьёт **только** мобов | `combat.cpp:1143` | — |
| 4 | Выстрел моба (`team == 0`) бьёт **только** толпу | `combat.cpp:1174` | — |
| 5 | Монстр не может задеть монстра | следствие 3 | «would silently invent monster-on-monster friendly fire» |

**Все пять закрыты. 3, 4, 5 — 2026-08-12 (§33), 1 и 2 — 2026-08-13.**

Абзац, стоявший здесь, говорил: «исключения 1 и 2 законны и должны остаться, они
про геометрию спавна; правильное решение — спавнить за пределами коллайдера **либо**
давать неуязвимость на первые N сантиметров». Первая половина верна, вторая была
лишней, и «должны остаться» оказалось неверно.

§33 сделала половину работы: вынесла дуло на `kMuzzleForward` = 1.7 м и удалила
`team`. Исключение 1 (`p.source != victim`) осталось стоять — с геометрическим
обоснованием, которого никто не посчитал. Счёт такой: дуло отмеряется от ГЛАЗА, а
попадание меряется от НАЧАЛА ТЕЛА, и между ними — рост. При выстреле строго вниз
зазор равен `kMuzzleForward - body_eye_height(h)`, что при максимальном росте,
который выдаёт `height_for_age` (2200 мм), даёт 0.754 м против сферы 0.75 м:
**4 мм**, держащиеся на согласии трёх констант в трёх файлах.

Правило страховало арифметику, которую не сделали, — ровно та же форма, что нашла
§33, когда правило страховало дуло, которое не поставили.

Починка — `muzzle_point`: решается выход луча из сферы попадания, и точка рождения
двигается дальше `kMuzzleForward` тогда и только тогда, когда иначе она осталась бы
внутри тела. Зазор становится гарантией при ЛЮБОМ росте, и правило удалено целиком.
Дистанция взведения не понадобилась: она хранила бы состояние на снаряде («сколько
я пролетел»), то есть память, — а вся суть в том, что снаряд не помнит ничего.

Проверено обеими полярностями: вернуть `&& p.source != victim` — краснеет один
CHECK (собственная пуля в собственном теле обязана ранить держателя камеры);
вернуть наивное смещение вместо `muzzle_point` — краснеет восемь (рост 2.3…3.0 м).

**Исключения 3, 4, 5 — прямое нарушение манифеста.** Это `team`-гейт, то есть
командная принадлежность, а игра заявлена как симулятор без команд: у неё есть
фракции с матрицей отношений 6×6, где враждебность — это **число**, а не
булев флаг стороны.

## 2б. Снаряды: пула нет, попадание по клеткам

### 2б.1. Количество снарядов ничем не ограничено

Снаряды — обычные сущности EnTT: `reg.create()` (`combat.cpp:868`, `:904`),
`reg.destroy` (`:1310`). **Ни пула, ни константы ёмкости.** Живёт
`kProjTtlMs = 4000` (`combat.h:380`).

Арифметика для дробовика `granit4u_belt_shotgun`: 12 дробин при откате 45 мс даёт
**≈12 × (4000/45) ≈ 1067 живых сущностей** при удержании гашетки. Каждая
интегрируется шагом 8 мс (`kSimDt = 1/125`, `core/tick.h:26-27`).

Ограниченное POD-кольцо в этом файле есть, но оно про **другое**:
`kMaxCarveProposals = 128` (`combat.h:600`), и вот **оно** молча роняет
(`:621`, `if (count >= kMaxCarveProposals) return false;`).

**Оценка:** отсутствие пула здесь не дефект по закону нулевых аллокаций — EnTT
пулит сущности сам. Дефект в том, что **число не названо**. Тысяча сущностей на
одно нажатие — это бюджет, и он обязан быть записан, чтобы регрессия была видна.

### 2б.2. Попадание по клеткам 2,0 м — нарушение закона гранулярности

```cpp
// combat.cpp:1199-1210
const int cx = wrap_macro(static_cast<int>(tr.pos.x / kCellSize));
...
if (cz < 0 || cz >= kMacroDim || grid.cell(cx, cy, wrap_macro(cz)) != kCellAir) {
```

`kCellSize = 2.0f` против `kVoxelSize = 0.25f` (`world/types.h:34-35`). Суб-воксельная
маска в дереве есть и используется рядом: `sim/physics.cpp:37-42` разрешает тела по
`kVoxelSize`, `world/stain.cpp:68` шагает по `kVoxelSize * 0.5f`.

**Снаряды разрешают геометрию в 8 раз грубее, чем физика тел в той же
симуляции.**

Комментарий `combat.h:1194-1196` защищает это намеренно: суб-воксельная маска
«пропустила бы снаряд через полу-выеденную клетку, которая читается как
сплошная». Довод понятен, но следствие **противоречит фиче, которую тот же файл
поставляет**: пули выедают суб-воксельные отверстия
(`kBulletCarveRadius = 0.35f`, `combat.h:643`), сквозь которые потом **не могут
стрелять**.

Игрок прорезает туннель — и его собственные пули останавливаются на входе, потому
что клетка по-прежнему не воздух. Это наблюдаемая игроком нелепость, а не
внутренний долг.

**Правильная форма починки** (не «включить маску»): вести луч по клеткам, а внутри
непустой клетки — по суб-маске. Дорого только там, где уже есть препятствие, то
есть в одной клетке из тысячи. Даёт и точность, и защиту от проскока.

### 2б.3. Гравитация на снарядах — вектор, и это образец

```cpp
// combat.cpp:1097-1103
const vec3 projG = stack.layer(layer).gravity().at(tr.pos);
const float projGLen = length(projG);
if (projGLen > 1e-6f) {
    const float mag = kProjGravity * (p.gravityPct * 0.01f) * dt;
    v.v = v.v + projG * (mag / projGLen);
}
```

Единичное направление × скалярная величина — закон соблюдён точно. `x`/`y`
обёрнуты тором, `z` намеренно нет (`:1104-1106`), что согласуется с охраной
`cz < 0 || cz >= kMacroDim` (`:1202`).

**Две утечки жёсткой оси остались в запуске**, обе `+z`:
`combat.cpp:866` — компенсация навесной траектории решает только по `z`;
`combat.cpp:871` — `tr.pos.z += 0.6f` как высота груди.

Под не-`NegZ` режимом моб прицелится навесом не в ту ось, пока

**Гранаты: механика есть с 2026-08-13.** Абзац выше держался ровно до тех пор,
пока `Projectile::team` не удалили (2026-08-12): правило сняли ради вещи, которой
в игре не было, и манифестное «осколки бьют и владельца» проверялось снарядом,
приставленным к стрелку вплотную. Пуля летит ОТ тебя — это не тот случай.

Что построено, все три части через существующие швы:

- **Отскок.** `ProjType::Grenade` не гибнет о геометрию, а отражается. Отражение
  считается от ГРАНИ клетки: шаг метётся против трёх плоскостей границ, берётся
  самое раннее пересечение, и нормаль — свойство этой грани. Ось-буква не
  участвует нигде — цикл `grenade_advance` в `combat.cpp` написан поверх
  индексного доступа `axis(v, a)`, поэтому у x/y/z нет и не может быть особого
  случая (закон изотропии, [problems.md] §34). Это не декларация: мутация
  «отражать самую большую компоненту скорости» проверена и падает на скользящем
  случае в `test_grenade`.
- **Детонация по истечении.** `ttlMs` — тот же таймер, что у пули, но для
  гранаты это ФИТИЛЬ: ноль означает взрыв, а не потраченный снаряд. Второго
  таймера нет намеренно.
- **Площадной урон без единого исключения.** Один проход по `NpcRef` и `MobRef`
  в радиусе, линейное затухание от расстояния, весь урон — через `apply_damage`.
  **Владельца в этом проходе не ищут.** `source` читается ровно дважды, оба раза
  чтобы записать убийство (XP и §40), никогда — чтобы кого-то пропустить.

Разрушение и частицы — через `CarveProposalQueue` и `ParticleBurstQueue`, ничего
нового не заведено; радиус выемки `kBlastCarveScale = 0.35` от радиуса урона,
потому что осколки летят дальше, чем ломается бетон. Взрыв ещё и слышно:
`blast_noise` — первый в дереве источник severity 5, ту ветку `weapon_fire_noise`
называл недостижимой именно потому, что площадного оружия не было.

предмета, радиус 2.5 клетки, фитиль 3.0 с) и три новые колонки

## 2в. Автомат состояний оружия: ни патронника, ни осечек

Состояние в `PlayerRanged` (`combat.h:331-338`): `cooldownMs`, `reloadMs`,
`magCount`, `weapon`. **Патронника как отдельного состояния нет. Осечки нет
нигде.**

| Из | Условие | В | Где |
|---|---|---|---|
| любое | тик | откаты декрементируются до любого выхода | `:1338-1339` |
| любое | оружие сменилось | `magCount = 0` — **смена высыпает магазин** | `:1351-1355` |
| Перезарядка | `reloadMs > 0` | заблокировано | `:1357` |
| Пусто | патроны есть | `reloadMs = 1000` (на всех 29 стволах) | `:1359-1378` |
| Пусто | патронов нет | остаётся пусто, **без блокировки** | `:1375` |
| Готово | `wantFire && cooldownMs == 0` | выстрел, `--magCount` | `:1417-1464` |

**Перезарядка автоматическая и непроизвольная.** Она срабатывает по
`magCount == 0` независимо от желания игрока, ручного ввода перезарядки нет.

Отсюда три отсутствующих механики, каждая — не «недоделка», а следствие формы
автомата:

- **Доснаряжение невозможно.** Магазин на 1/30 нельзя пополнить, пока он не
  опустеет полностью. Тактика «перезарядиться до боя» не выразима.
- **Осечек и износа нет.** `ranged_table.h:30-34` фиксирует нулевую прочность на
  всех строках. Ждёт систему износа из [спеки 03](03_ECONOMY_MASS_AND_CRAFTING.md).
- **Сухой щелчок неотличим от отсутствия ввода.** Ветка «пусто» возвращает 0 до
  проверки `wantFire` (`:1381`), поэтому `pr.shots` не растёт и обратной связи нет.
  Игрок, у которого кончились патроны, не получает **никакого** сигнала.

Последнее — самое дешёвое к починке и самое заметное в игре.

## 6. Явные не-цели

- ~~**Не убирать исключения 1 и 2.**~~ **Отменено 2026-08-13 — эта не-цель была
  неверна.** Правая половина её верна и сегодня: снаряд, рождающийся внутри
  коллайдера стрелка, — геометрическая проблема. Но вывод «значит, исключение
  остаётся» не следует: геометрию можно починить НАСОВСЕМ (`muzzle_point` решает
  выход луча из сферы попадания при рождении), и тогда исключению нечего оплачивать.
  Дистанция взведения тоже не нужна и хуже: она возвращает снаряду память о

- **Не расширять до 8 атрибутов до того, как заработает INT.** Три атрибута, из
  которых один декоративен, — это не «мало атрибутов», это «атрибут без
  потребителей». Восемь таких будут хуже трёх.
- **Не клампить отрицательный резист в ноль.** Уязвимость — заявленная механика
  (`combat.cpp:49-50`).
- **Не трогать конус разброса.** Он уже исправлен под 3D с письменным
  обоснованием (`combat.cpp:1389-1391`).
