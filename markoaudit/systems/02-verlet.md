## 3. Различия, которые НЕЛЬЗЯ схлопнуть (раздел «против»)

Честно, не формально. Пять из них настоящие.

**3.1. Размер записи различается в 16 раз.**
64 B у частицы (`particle_pass.h:40`) против 1040 B у листа
(`cloth_pass.h:37`). Единый AoS-массив по 1040 B под 32768 частиц = 34 МБ
вместо 2 МБ — семнадцатикратный перерасход VRAM и полное уничтожение
локальности кэша у частичного прохода. **Один AoS-буфер на все три вида
невозможен.**

**3.2. Гранулярность потока противоположна.**
Провод/ткань: ОДНА инвокация обрабатывает ВЕСЬ элемент (8 или 32 точки), потому
что решатель связей идёт последовательно и не требует синхронизации
(`wire_sim.comp:102`, `cloth_sim.comp:102`). Частица: одна инвокация = одна
точка (`particle_sim.comp:44`). Диспатчи считаются по разным величинам:
`(chainCount_+63)/64` (`wire_pass.cpp:318`) против `(kMaxParticles+63)/64`
(`particle_pass.cpp:292`). Слить в один `gl_GlobalInvocationID` без косвенной
таблицы «id → (вид, элемент)» нельзя.

**3.3. Число точек — компилтайм-константа в разворачиваемом цикле.**
`for (int k = 0; k < 8; ++k)` (`wire_sim.comp:78`) и
`for (int k = 0; k < W*H; ++k)` (`cloth_sim.comp:80`, `W=8,H=4`,
`cloth_sim.comp:66-67`) разворачиваются компилятором в регистры. Динамическая
граница из push-константы убьёт разворот и добавит ветвление в горячем цикле.
Смягчается специализационными константами, но это не «бесплатно».

**3.4. Время жизни принципиально разное.**
Частица — расходник: `posLife.w -= dt`, `<=0` = мертва и слот переиспользуется
кольцевым курсором (`particle_pass.cpp:265-266`). Провод/ткань — постоянное
состояние этажа, загруженное `upload()` один раз при входе
(`main.cpp:1136`, `:1183`) и живущее до смены этажа. У провода нет курсора,
нет спавна, нет смерти — есть `meta.y` от CPU-зонда. Кольцевой аллокатор для
проводов не нужен и вреден.

**3.5. Дескрипторы различаются по составу.**
wire/cloth: 3 SSBO (элементы, тела, маски), `wire_pass.cpp:62-78`.
particle: 2 SSBO (пул, маски), `particle_pass.cpp:59-67`, буфера тел НЕТ вовсе.
Плюс `stageFlags` у binding 0 — `COMPUTE|VERTEX` во всех трёх, значит SSBO
шарится с рисующим шейдером и его раскладка завязана ещё и на
`wire.vert:8-13` / `cloth.vert` / `particle.vert:12-18`. **Три вертексных
шейдера тоже придётся трогать** (`diff wire.vert cloth.vert` = 72 строки,
`diff wire.vert particle.vert` = 88).

**3.6 (слабое, схлопывается).** «Разная частота обновления» — заявленного
различия НЕТ: все три вызываются один раз за КАДР с `dt = 1.0f/60.0f`
(`main.cpp:6903`, `:6934`, `:6954`). Это не аргумент против слияния, это баг
(см. §6.2).

VRAM ради четырёх чисел HUD в одной клетке под игроком** — газ никем не
визуализируется (`grep -l gas shaders/` → только сам `gas_sim.comp`) и не влияет
ни на здоровье, ни на потребности (единственные потребители — `hud_ui.cpp:130-147`).
Это тема отдельного отчёта, не этого.

### 4.5 БАГ: `wireFall`/`clothFall` сбрасываются только по смене КОЛИЧЕСТВА

```cpp
// src/app/main.cpp:6887-6888
static game::FallClock wireFall;
if (wireFall.left.size() != ab->wires.size()) wireFall.clear();
```
```cpp
// src/app/main.cpp:6917-6919
static game::FallClock clothFall;
if (clothFall.left.size() != ab->cloths.size()) clothFall.clear();
```

`FallClock::step` (`antourage.h:214-229`) хранит три состояния во float:
`-1` = держится, `>0` = падает, `0` = **истрачен и остаётся истраченным**
(строка 220: `if (left[i] == 0.0f) return false;`).

Обе переменные — `static` в теле цикла кадра, то есть переживают смену этажа.
Единственное условие сброса — **изменение размера**. `step` доращивает вектор
до `i+1` (строка 215), значит после полного прохода `left.size()` ровно равен
числу элементов бейка. Следовательно:

> Если игрок уходит с этажа, где N проводов, и приходит на этаж, где тоже N
> проводов, `wireFall.clear()` НЕ вызывается. Провода нового этажа наследуют
> счётчики старого: те, что были «истрачены» (`left[i]==0`), на новом этаже
> сразу возвращают `false` → `write_alive` кладёт 0 → `wire_sim.comp:72`
> выходит, `wire.vert:44` клипает. **Провода на свежем этаже не появляются
> вовсе, без единого сообщения.**

Индекс `i` — позиция в `ab->wires`, у нового этажа это совершенно другой
провод. Классификация: **БАГ**. Правильный ключ сброса — (этаж, слой), ровно
как у газа рядом: `main.cpp:6826-6830` уже держит `gasSeedFloor`/`gasSeedLayer`
и делает это правильно. Образец лежит в 60 строках выше.

## 5. Шов CPU↔GPU: их ТРИ, а не один

Канон требует одного шва. Проверено — путей три, и они не сходятся.

### Путь A — `GpuHandoff` (проп рассыпается в частицы)
```cpp
// src/game/prop_system.cpp:81-103
if (mode == PropFallMode::GpuHandoff) {
    if (bursts != nullptr) { ... bursts->push(pos, dir, ParticleKind::Debris, 6, matId, seed ^ 0xD3B15u); }
    reg.destroy(prop);
    return;
}
```
Сущность уничтожается, в очередь `ParticleBurstQueue` кладётся всплеск.
Очередь сливается в GPU-пул в `drain_particle_bursts` (`main.cpp:1229-1247`),
вызов — `main.cpp:4465`. **Это правильный шов, и он единственный правильный.**

### Путь B — `DetachedPiece`: severed антураж идёт на **CPU**, не на GPU
```cpp
// src/game/antourage/antourage.cpp:856-892 — carve_step заполняет `fell`
DetachedPiece d{}; ... d.life = kAntourageFallSec;
```
```cpp
// src/app/main.cpp:6768-6770
if (!antourageFalling.empty())
    game::antourage_detach_step(stack.layer(activeLayer), antourageFalling, frameDt);
```
`antourage_detach_step` (`antourage.cpp:716-761`) — **ЧЕТВЁРТЫЙ интегратор**,
на CPU, со СВОЕЙ коллизией (`aabb_overlaps_solid`, строка 735), своим
демпфированием (`-0.18f` строка 751, `0.6f`/`0.5f` строка 756-757) и своим
таймером жизни. Отрисовывается через `PropPass` как обычный инстанс
(`main.cpp:1356-1367`).

Это **прямое расхождение с каноном задания**: «антураж — GPU». Кусок трубы,
отрезанный карвом, летит на CPU-физике. Комментарий в `antourage.h:239-245`
это признаёт и обосновывает («collides against the SOLVER's own predicate…
headless-testable»), но канон владельца в задании говорит другое. Кто прав —
решение владельца, не аудита; фиксирую факт: **режущий удар по трубе и режущий
удар по пропу с `GpuHandoff` уходят в РАЗНЫЕ миры физики.**

### Путь C — прямой `spawn()` мимо очереди
Три места пишут в GPU-пул минуя `ParticleBurstQueue`:

| Место | Код |
|---|---|
| `main.cpp:4040` | `spawn_carve_particles(particlePass, carveResult, ...)` |
| `main.cpp:4395` | `spawn_carve_particles(...)` — второй вызов |
| `main.cpp:4437` | `particlePass.spawn(dripTmp.data(), ...)` — капли с обрубков труб |

`spawn_carve_particles` (`main.cpp:1253`) сам собирает `GpuParticle` и зовёт
`pass.spawn` напрямую. То есть **шва два даже внутри частиц**: очередь и
прямой вызов. Разница наблюдаемая: очередь ограничена (`ParticleBurstQueue` —
POD-кольцо), прямой путь — нет.

**Итог §5: швов три (A: очередь→пул, B: CPU-тело DetachedPiece, C: прямой
spawn мимо очереди). Канон требует одного.**

## 7. ПРЕДЛОЖЕНИЕ: один `verlet_sim.comp`

### 7.1 Раскладка буферов — **SoA по видам, а не один AoS**

Обоснование прямое: §3.1 доказывает, что единый AoS невозможен (1040 B × 32768
= 34 МБ). Предложение — **разделить состояние и метаданные**:

```
Буфер 0: VerletPoint points[]      — 32 B на ТОЧКУ, плоский общий пул
    vec4 cur;   // xyz позиция, w = invMass (0 = пиннинг)
    vec4 prev;  // xyz прошлая позиция, w = life (для вида point; <0 = н/д)

Буфер 1: VerletElement elems[]     — 32 B на ЭЛЕМЕНТ, общий
    uint  kind;      // 0 chain | 1 sheet | 2 point
    uint  first;     // индекс первой точки в points[]
    uint  countW;    // ширина решётки (chain: длина, point: 1)
    uint  countH;    // высота решётки (chain/point: 1)
    float restX;     // горизонтальный rest
    float restY;     // вертикальный rest
    float invMassScale; // ВЫВЕДЕНО из массы элемента, не константа
    float alive;     // >0.5 живой

Буфер 2: vec4 bodies[]             — ОДИН на всех (сейчас два, §4.3)
Буфер 3: uint masks[]              — VoxelMirror, уже общий
Буфер 4: vec4 pointAux[]           — только для kind==point:
    colorSize + phys (цвет/размер/gravMul/drag/bounce/emissive)
```

**Почему так, а не иначе:**
- Провод = элемент с 8 точками, лист = с 32, частица = **элемент с 1 точкой**.
  Единый пул `points[]` даёт частице ровно её 32 B и не платит за `meta`.
- `pointAux` отдельным буфером — потому что провод не имеет цвета на точку, а
  частица имеет. Разнести, а не расширять общую запись.
- SoA (points отдельно от elems) — потому что горячий цикл интегрирования
  трогает ТОЛЬКО `cur`/`prev`, и на 32768 точек это линейный проход по 2 МБ
  вместо страйда по 1040 B.

### 7.2 Push-константы — только читаемые поля

```glsl
layout(push_constant) uniform Push {
    vec4 sim;   // x = dt, y = elemCount, z = bodyCount, w = wrapPeriod
    vec4 grav;  // xyz = вектор ускорения, w = ЧИСЛО ИТЕРАЦИЙ решателя (float)
} pc;           // 32 байта вместо 48+48+32=128
```
Все 10 мёртвых float из §4.1 исчезают. Демпфирование убрано из push совсем —
оно приезжает из `invMassScale` элемента, потому что выводится из массы
(закрывает §4.2 и §6.2).

### 7.3 Диспатч

**Два вызова, не один и не три.**

```
Проход 1 (интегрирование): один поток на ТОЧКУ.
    vkCmdDispatch((totalPoints + 63) / 64, 1, 1)
    Читает points + elems (через обратный индекс), масок, тел.
    Полностью параллелен, коллизий записи нет.

Проход 2 (связи): один поток на ЭЛЕМЕНТ, ранний выход для kind==point.
    vkCmdDispatch((elemCount + 63) / 64, 1, 1)
    Ровно текущая схема wire/cloth (§3.2), их последовательный решатель
    сохраняется как есть — он корректен и не требует синхронизации.
    Частицы просто выходят на первой строке.
```

Разделение обязательно: §3.2 показывает, что гранулярность потока у частиц и у
цепей противоположна. Два прохода снимают это противоречие ценой одного лишнего
`vkCmdDispatch` и одного барьера — дешевле, чем 32768 потоков, из которых 31 000
простаивают в ветке `if (kind != point)`.

**Топология связей** решается без ветвления по виду: `chain` = решётка
`countW×1`, `sheet` = `countW×countH`, `point` = `1×1`. Общий двойной цикл по
решётке (горизонталь + вертикаль) даёт цепь автоматически при `countH==1`
(вертикальный цикл `for r < H-1` не выполняется ни разу). **Отдельного кода под
цепь не нужно вообще** — это главная находка обобщения: `cloth_sim.comp:104-132`
уже содержит `wire_sim.comp:103-114` как частный случай `H=1`.

**Пиннинг и якоря сохраняются как есть**: `cur.w == 0` — единственный признак
закреплённой точки во всех трёх симах уже сегодня (`wire_sim.comp:80`,
`cloth_sim.comp:82`). `write_pins` обоих пассов пишет в тот же слот
(`wire_pass.cpp:278`, `cloth_pass.cpp:277`) — сливаются в один метод с
`uint64_t` маской (покрывает и 8, и 32 точки). `meta.y`/`life` объединяются в
`elems[].alive`.

### 7.6 Как доказать, что поведение НЕ изменилось

Слепая проверка «оно выглядит так же» здесь не годится: провод провисает
одинаково при заметно разных константах. Нужны числовые замеры ДО и ПОСЛЕ, на
одном сейве, одном этаже и одном сиде.

**Замер 1 — форма провисания (числовой, уже есть инструмент).**
`main.cpp:1155-1159` под `GIGA_WIRE_DBG` печатает середину каждой цепи:
```
[wire] %zu mid (%.1f %.1f %.1f)
```
Аналог для ткани — `main.cpp:1185-1189` (`cur[3]`, верхняя точка).
Протокол: `GIGA_WIRE_DBG=1 ... --floor 5`, снять stderr ДО правки, снять ПОСЛЕ,
`diff`. Загрузка ставит верле в позу покоя (`upload_wires` пишет
`prev == cur`, `main.cpp:1147-1148`), поэтому первая печать **обязана совпасть
побайтово** — она проверяет упаковку, а не физику.
Ограничение, которое надо назвать честно: печать идёт при `upload`, то есть до
первого шага сима. Для установившегося провисания нужен второй замер — добавить
ту же печать после N шагов, иначе тест проверяет только загрузку.

**Замер 2 — покой (главный, ловит изменение демпфирования и итераций).**
Через `alive_count()`-подобный проход по mapped-буферу: после 600 шагов без
тел рядом сумма `|cur - prev|` по всем точкам должна лежать ниже порога и
совпадать ДО/ПОСЛЕ с точностью 1 %. Провод в покое — это функция ТОЛЬКО от
демпфирования и числа итераций; если 0.985 заменён выводом из массы, этот
замер обязан показать расхождение, и это будет ЖЕЛАЕМОЕ расхождение, которое
надо предъявить владельцу отдельно, а не спрятать в рефакторинг.

**Замер 3 — частицы, счётчик живых.**
`particlePass.spawned_total()` (`particle_pass.h:73`) и `alive_count()`
(`particle_pass.h:77`) уже выводятся в HUD (`main.cpp:5205`). Протокол:
`GIGA_PARTICLE_DBG=3` (фонтан искр перед камерой, `main.cpp:4447-4470`),
зафиксировать `alive` на 100-м, 300-м, 600-м кадре. Кривая живых частиц —
прямая функция `life`, `drag` и `bounce`; она обязана совпасть ДО и ПОСЛЕ,
потому что эти три величины по проекту берутся из записи частицы, а не из кода.

**Замер 4 — производительность, честная.**
`renderer.timer` уже брекетит `gpu::GpuPass::SimPhysics` вокруг всех трёх
compute-записей (`main.cpp:6873` … `:6956`) и вычитаемый под-брекет
`VoxelFlush` (`main.cpp:6942-6945`). Это ровно та величина, которую слияние
должно улучшить. Снять медиану SimPhysics за 600 кадров ДО и ПОСЛЕ.
**Обязательная страховка перед замером** (ловушка из памяти проекта): проверить
`CMakeCache.txt` на `CMAKE_BUILD_TYPE=Release` — сборка в Debug даёт ~10× по
кадру и выглядит как регрессия правки.

**Замер 5 — обратная полярность (проверить, что тест вообще что-то ловит).**
Перед тем как писать «замеры сходятся», намеренно сломать: поставить
`it < 3` вместо `it < 4` в объединённом решателе и убедиться, что Замер 2
показывает расхождение. Если не показывает — тест не проверяет ничего, и
«сошлось» ничего не значит.

**Чего проверить НЕЛЬЗЯ, и это надо сказать прямо.**
Тестов на GPU-симы в репозитории НЕТ. `grep -rln "verlet|wire_sim|GpuWireChain|
GpuParticle|GpuClothSheet" tests/` даёт РОВНО один файл — `suite_antourage.inl`,
и он покрывает только CPU-половину (бейк, `FallClock`, `antourage_carve_step`).
`suite_particles.inl:6-7` признаёт это прямым текстом: «The GPU half is
render-side and deliberately untestable headless». Значит `ctest` **не поймает
ни одной регрессии этого слияния**. Все пять замеров выше — ручные, на живом
запуске. Это и есть главный риск работы.
