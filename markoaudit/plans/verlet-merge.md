## 2. Целевая схема

### 2.1 Раскладка буферов — SoA, фиксированные регионы

Утверждение канона «единый AoS дал бы 34 МБ вместо 2» **перепроверено и верно**:
максимальная запись = лист, 1040 Б (`static_assert` `cloth_pass.h:37`), максимальная
популяция = частицы, 32768 (`particle_pass.h:42`); 1040 × 32768 = 34 078 720 Б ≈ 34 МБ
против нынешних 2 МиБ пула частиц (64 × 32768 = 2 097 152 Б,
`particle_pass.h:40`). Уточнение для честности: 34 МБ — это цена AoS только у
частичного региона; все три буфера сегодня суммарно ≈ 2.8 МиБ (272К wire + 520К
cloth + 2М particle).

Предлагаемая раскладка (развитие §7.1 аудита, с упрощением — без косвенной таблицы):

```
binding 0: VerletPoint points[]   — 32 Б/точку, единый пул, ФИКСИРОВАННЫЕ РЕГИОНЫ:
    vec4 cur;   // xyz позиция, w = invMass (0 = пиннинг)
    vec4 prev;  // xyz прошлая позиция, w = life остаток (антураж: -1 = вечный)
  [0 .. 8191]      wire:  1024 цепей × 8
  [8192 .. 24575]  cloth: 512 листов × 32
  [24576 .. 57343] particle: 32768 × 1
  = 57344 × 32 Б = 1.75 МиБ

binding 1: VerletElement elems[]  — 32 Б/элемент, ТОЛЬКО wire+cloth (1536 шт = 48 КиБ):
    uint  first;     // индекс первой точки в points[]
    uint  countW;    // цепь: 8, лист: 8
    uint  countH;    // цепь: 1, лист: 4   ← «цепь = решётка при H=1»
    float restX;     // горизонтальный rest (meta.x сегодня)
    float restY;     // вертикальный rest (meta.z сегодня; цепь: не читается, H=1)
    float dampRate;  // γ, 1/с — ВЫВЕДЕНО из массы, см. §3
    float alive;     // >0.5 живой (meta.y сегодня)
    float _pad;

binding 2: vec4 bodies[]          — ОДИН буфер вместо двух дублей (§4.3 аудита)
binding 3: uint uMasks[]          — VoxelMirror, уже общий
binding 4: ParticleAux aux[]      — 32 Б/частицу, только регион частиц (1 МиБ):
    vec4 colorSize; // rgb + размер билборда (как сегодня)
    vec4 phys;      // gravMul / dragRate / bounce / emissive (как сегодня)
```

Почему регионы, а не таблица «точка → элемент»: раз размеры элементов
компилтайм-константы (8 / 32 / 1), принадлежность и локальный индекс считаются
арифметикой от `gl_GlobalInvocationID` — косвенный буфер не нужен, кэш не
страдает. У частиц нет записей в `elems[]` вообще: **«ноль связей» выражается
тем, что регион частиц просто не входит в диспатч связей** (см. 2.3), а не
ранним выходом 32768 потоков.

Итого VRAM: 1.75 МиБ + 48 КиБ + 1 МиБ + 8 КиБ ≈ 2.8 МиБ — паритет с сегодняшним,
в 12 раз меньше наивного AoS.

### 2.2 Один comp-шейдер

Один файл `shaders/verlet_sim.comp`, одна пайплайн, фаза — в push-константе
(ветка по фазе когерентна на весь диспатч, цены не имеет). `solid_at`,
`world_land`, толчок телами — по одной копии вместо 3/2/2.

### 2.3 Два диспатча

```
Проход 1 — ТОЧКИ (интеграция + тела + коллизия о мир):
    vkCmdDispatch((totalPoints + 63)/64, 1, 1)
    1 поток = 1 точка. Верле-шаг, толчок телами (для региона частиц bodyCount
    эффективно 0 или общий — см. §7 в.5), world_land / отражение по bounce.
    Полностью параллелен: пишет только свою точку.
барьер compute→compute
Проход 2 — СВЯЗИ (только антураж):
    vkCmdDispatch((elemCount + 63)/64, 1, 1)   // elemCount ≤ 1536 → 24 группы
    1 поток = 1 элемент, последовательная релаксация как сегодня
    (wire_sim.comp:102, cloth_sim.comp:102 — корректна, синхронизации не требует).
    Общий двойной цикл по решётке W×H: горизонталь + вертикаль; при H=1
    вертикальный цикл `for (r < H-1)` не исполняется ни разу — цепь получается
    автоматически, отдельного кода под неё НЕТ (главная находка аудита:
    cloth_sim.comp:104-117 при H=1 повторяет wire_sim.comp:103-114 в том же
    порядке обхода — есть шанс на побитовое совпадение, см. §6).
```

Это снимает противоречие гранулярности (§3.2 аудита): сегодня wire/cloth — поток
на элемент, particle — поток на точку; в целевой схеме интеграция ВЕЗДЕ
поточечная (для цепей это даже выигрыш параллельности), связи — поэлементные.
Ловушка §3.3 аудита (компилтайм-развёртка `for k<8`) уходит вместе с самим
циклом: в проходе 1 цикла по точкам больше нет; в проходе 2 границы `W×H ≤ 32` —
динамические, но элементов всего ≤1536, это холодный диспатч.

### 2.4 Унифицированный SimPush — обезвредить ODR-ловушку

Сегодня в `namespace giga::gpu` живут ТРИ разных `struct SimPush` в трёх
анонимных namespace (`wire_pass.cpp:40`, `cloth_pass.cpp:40`, `particle_pass.cpp:40`),
две по 48 Б, одна 32 Б, и **`sim.w` означает разное: демпфирование у wire/cloth,
период тора у particle**. При слиянии .cpp в один TU это ODR-нарушение.
Порядок работ обязан начаться с нового имени и новых имён полей, а не с
копирования старых:

```glsl
layout(push_constant) uniform VerletPush {
    vec4 counts; // x totalPoints, y elemCount, z bodyCount, w phase (0/1)
    vec4 sim;    // x dt, y wrapPeriod, z solverIters, w unused
    vec4 grav;   // xyz вектор ускорения (m/s^2) — NEVER assume -Z, w unused
} pc;            // 48 Б вместо 48+48+32 = 128
```

Демпфирования в push НЕТ вовсе — оно per-element (`dampRate`, §3) и per-particle
(`aux.phys.y`). 10 мёртвых float из §4.1 аудита исчезают по построению.

### 2.5 Заворачивание позиций — параметр вида, не унификация

Частица заворачивает позицию (`mod(cand, per)` `particle_sim.comp:71`), антураж —
нет: его констрейнты считают `B.xyz - A.xyz` в НЕзавёрнутых координатах
(`wire_sim.comp:106`), и заворот позиций порвал бы связь через шов ошибкой ±per.
В целевой схеме wrap позиции — свойство региона (частицы: да, антураж: нет).
Альтернатива — торус-дельты в решателе и заворот всех — трогает и три
vert-шейдера, и бейк; отложить (§7 в.9).

### 2.6 Что остаётся тремя

Рисующие пассы: лента (`wire.vert`), двусторонний квад (`cloth.vert`), билборд
(`particle.vert`) — три разных примитива, три графических пайплайна внутри
одного класса. Их SSBO-чтение переезжает на новую раскладку СИНХРОННО с
шейдером сима — это риск №1 (валидация Vulkan расхождение раскладки не ловит,
вершины просто тихо поедут; §7.5 аудита).

## 3. Вывод констант: демпфирование из массы

Факт: `main.cpp:1143` пишет массу цепи в `meta.z`:
```cpp
g.meta = vec4{c.restLen, 1.0f, c.massKg, 0.0f};
```
`massKg` честно выводится в бейке из погонной плотности:
`c.massKg = spanM * kWireKgPerMetre` (`antourage.cpp:608`, `kWireKgPerMetre = 0.35f`
`antourage.cpp:534`). Но `wire_sim.comp` читает только `meta.x` (`:75`) и `meta.y`
(`:72`) — **масса пакуется каждую загрузку этажа и не читается никем**, а
демпфирование при этом — литерал `0.985f` (`wire_pass.cpp:312`), одинаковый для
любого кабеля. Прямое нарушение закона «константа выводится из свойств объекта».

**Вывод.** Демпфирование верле — это линейное вязкое трение о воздух:
`v(t+dt) = v·exp(-γ·dt)`, где `γ = b/m` (коэффициент сопротивления на массу).
Для кабеля сопротивление пропорционально обдуваемой поверхности,
`b_точки = k_air · π·d · (span/8)`, а масса точки `m_точки = λ·span/8`
(λ = `massKg/spanM` — погонная плотность). Длина сокращается:

```
γ = k_air · π·d / λ        [1/с]
dampRate (elems[].dampRate) = γ;  в шейдере: vel *= exp(-γ·dt)
```

Свойства объекта в формуле: `d` — диаметр кабеля (сегодня зашит как
`kHalfWidth = 0.022` в `wire.vert:29` — должен приехать из бейка тем же путём,
что и масса), `λ` — из `massKg/spanM`, которые бейк уже считает.

**Калибровка, чтобы картинка не дёрнулась:** сегодняшний `0.985` на шаге
`dt=1/60` — это `γ₀ = -ln(0.985)·60 ≈ 0.907 1/с`. Полагаем
`k_air = γ₀·λ₀/(π·d₀) ≈ 0.907·0.35/(π·0.044) ≈ 2.30 Н·с/м³` — тогда эталонный
кабель (λ=0.35, d=0.044) воспроизводит сегодняшнее поведение ТОЖДЕСТВЕННО, а
кабель другой плотности/толщины демпфируется иначе — тяжёлый качается дольше,
лёгкий глохнет быстрее. Вывод записан, происхождение каждого числа видно.
Для ткани — та же формула с поверхностной плотностью (кг/м² × площадь точки).

Бонус той же формулы: `exp(-γ·dt)` корректен при ЛЮБОМ dt — попутно чинится
и `pow(drag, dt*60)` частиц (`particle_sim.comp:61`, 60 Гц зашито при
`kSimHz=125`): `aux.phys.y` превращается из «drag за шаг 60 Гц» в γ тем же
пересчётом `γ = -ln(drag)·60` на CPU при паковке — таблица `particles.csv` не
меняется.

## 6. ВЕРИФИКАЦИЯ (главный раздел)

Исходное положение, честно: **тестов на GPU-симы нет вообще.**
`suite_particles.inl:6-7` прямо пишет «The GPU half is render-side and
deliberately untestable headless»; `suite_antourage.inl` (842 строки) покрывает
только CPU-половину (бейк, `wire_live_pins`, `FallClock`). `game_test`/
`world_test` — headless без Vulkan, `ctest` не исполняет ни одной строки GLSL и
**не поймает ни одной регрессии этого слияния**. Механизм надо ПОСТРОИТЬ до
первой правки (шаг 1 этапа 1).

### 6.1 Пин-механизм: хеш состояния из mapped-буферов (локально, с GPU)

Ключевой факт, который делает пин дешёвым: все три state-буфера —
host-visible и постоянно замаплены (`points_.create_host_visible`
`wire_pass.cpp:53-55`; `alive_count()` уже сегодня читает пул с CPU,
`particle_pass.h:77-84`). Значит снимок состояния — это проход по указателю,
без каких-либо Vulkan-ридбеков.

Предложение — `GIGA_VERLET_PIN=N` в main.cpp (~40 строк, единственный новый
код вне слияния):
- счётчик **записанных симов** (инкремент рядом с `record_sim`), НЕ кадров и НЕ
  тиков — харнесс `--shot` открывает панели и ставит паузу, счёт `tick=`
  между прогонами не сходится (проверено ранее: один бинарь давал то 2820, то
  120 тиков); присентед-кадры (`shotFramesSeen` `main.cpp:7049`) тоже не
  годятся — сим может быть не записан в кадре;
- на N-м симе: `vkDeviceWaitIdle`, проход по mapped `points`/пулу, печать в
  stderr (а) FNV-1a-хеша над `cur.xyz`, квантованными до 1e-3 м, (б) полного
  дампа позиций в файл (для допускового сравнения), (в) `alive_count`;
- прогон: `--shot /tmp/pin.png --frames 900 --floor 5` на фиксированном сейве
  (стереть стейл-сейв перед прогоном — закон из padic-эпика), Release-сборка
  (проверить `CMakeCache.txt`: Debug даёт ~10× по кадру и маскирует всё);
- **детерминизм входов**: для базлайна тела не подавать (пин-флаг зануляет
  `upload_bodies` — толпа недетерминирована), карва нет → маски статичны,
  гравитация — константа слоя. Тогда антураж детерминирован полностью.
  Для частиц — синтетический burst с фиксированным сидом под тем же флагом
  (`pack_particles` уже детерминирован от сида, `main.cpp:1210-1227`);
  `GIGA_PARTICLE_DBG=3` (фонтан, `main.cpp:4444-4470`) годится, если его сид
  фиксирован — проверить при постройке пина.

### 6.2 Двухуровневое сравнение: где побитово, где допуск

- **Побитово (хеш):** шаги, не меняющие математику — шаг 2 этапа 1 (слияние C++
  при старых шейдерах) ОБЯЗАН дать тот же хеш; шаг 3 (раскладка) — тоже, если
  порядок операций в шейдере не тронут; шаг 4 — есть реальный шанс (порядок
  обхода связей H=1 совпадает с wire дословно), закладываться нельзя.
  На одной машине/драйвере при неизменном диспатче GPU-математика
  воспроизводима — базлайн гонять дважды подряд и убедиться, что хеш стабилен,
  ПРЕЖДЕ чем верить ему.
- **Допуск (дамп позиций):** где математика меняется законно (шаг 4 при
  несовпадении порядка fp-операций, весь этап 2): по-точечно
  `|Δcur| < 1 мм` после 900 симов и метрика покоя `Σ|cur-prev| < ε` — провод в
  покое есть функция только демпфирования и итераций, это самый чувствительный
  индикатор (§7.6 аудита, замер 2).
- **Кривая живых частиц** (этап 2): `alive_count` на 100/300/600-м симе при
  фиксированном фонтане — прямая функция life/drag/bounce.
- **Перф:** GPU-таймер уже брекетит всё слияние: `gpu::GpuPass::SimPhysics`
  (`main.cpp:6873`/`:6956`) минус под-брекет `VoxelFlush` (`:6942-6945`).
  Медиана за 600 кадров до/после.

### 6.3 Обратная полярность — прежде чем верить «сошлось»

Закон из памяти проекта: прогнать мутацию ДО записи утверждения. Перед началом
работ намеренно сломать: (а) `it < 3` вместо `it < 4` — хеш и метрика покоя
обязаны разойтись; (б) `0.985 → 0.98` — метрика покоя обязана разойтись;
(в) сдвинуть один пин — хеш обязан разойтись. Если какой-то из трёх не ловится
— пин не проверяет ничего, чинить пин, не начинать слияние.

### 6.4 Что проверяемо headless (попадает в ctest) — и что нет

Проверяемо и предлагается добавить:
- **лочстеп-паковка**: вынести `upload_antourage` из main.cpp (шаг 3) → голден-
  тест байтов упаковки фиксированного бейка (ловит дрейф CPU-стороны раскладки,
  половину лочстепа); `static_assert` на размеры записей уже есть — сохранить;
- **пересчёт констант**: юнит на `γ = -ln(0.985)·60` и калибровку §3 (чистая
  математика); юнит на арифметику регионов точка↔элемент (она задублируется
  в C++ паковке и в GLSL — пусть хоть C++-половина будет под тестом);
- CPU-половина антуража уже покрыта `suite_antourage.inl` — не трогается.

НЕ проверяемо headless, только локальный GPU-прогон (§6.1) и глаза:
- сам GLSL: интеграция, коллизия, констрейнты — пин 6.1 ловит числа, но он
  ручной и в CI не попадёт (в CI нет Vulkan-устройства);
- согласование sim-шейдера с ТРЕМЯ vert-шейдерами — расхождение раскладки не
  детектируется ничем, кроме картинки; риск №1 всего плана;
- качество движения: форма провисания, хлыст обрезанного конца, отскок искр —
  только глазами (`--shot` PNG на фиксированном кадре — слабое подспорье,
  прогоны нестабильны по наполнению кадра).

Формулировка для владельца без прикрас: ctest после всей работы будет ловить
паковку и арифметику, но НЕ физику; физику держит ручной пин-протокол 6.1-6.3,
записанный в план как обязательные шаги, плюс глаза на этаже 5.
