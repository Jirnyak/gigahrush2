# Единая система фонового допекания (async rebake) — дизайн

Статус: план для обсуждения с владельцем, 2026-08-18. Код не менялся.

Требование владельца (мягкая формулировка, 2026-08-18): мир мутирует вечно, поэтому не
событийный «перебейк по условию», а постоянный фоновый процесс. Секунды устаревания —
норма; порядка минуты — запечённое обязано стать актуальным. Система одна на все поля и
механики; она же обслуживает «поездку в лифте» (этаж генерится и печётся, пока игрок
заперт в кабине).

## 0. Что есть сейчас (факты из кода)

- `nav::AsyncBake` (`src/world/nav_async.h:42`, `nav_async.cpp:19-79`): один воркер на
  весь бейк, свап в `poll()` на главном потоке — единственная точка записи живого графа
  (`nav_async.h:74-80`). Измерено: coarse ~1.9 s + fine ~1.8 s на 20 потоках
  (`nav_async.h:6-7`). Воркер держит **сырой указатель** на живой `MacroGrid`
  (`nav_async.cpp:53`), контракт — «не мутировать World до ready()» (`nav_async.h:19-23`).
- Гейт `doors.frozen` (`src/game/door.h:154-161`, правило порядка `door.h:52-57`):
  выставляется перед каждым `begin_floor_nav` (main.cpp:1978, 2621, 4818, 7171),
  снимается в `poll()`-ветке (main.cpp:2758-2767). Пока он стоит: консольный карв
  откладывается (`main.cpp:4005`), боевые карвы **выбрасываются** (`main.cpp:4351-4354`,
  счётчик `droppedBake`), F9-загрузка отказывает (`main.cpp:4646-4651`).
- `begin_floor_nav` (`main.cpp:1381-1413`) заодно **синхронно** печёт room zones
  (`main.cpp:1396`, тайминг печатается строкой `[rooms]` — main.cpp:1400-1404).
- Инкрементальный патчинг nav признан тупиком и удалён 2026-08-06 (`src/world/nav.h:124-135`):
  `flow[узел]` — это BFS от узла через весь тор, карв в любой точке инвалидирует все 64
  поля. Вывод истории: **фоновый поток легитимен, инкрементальный BFS — нет**.
- `diffusion_mark_cell` готов (O(1), `src/sim/diffusion.cpp:152-164`) и имеет **0
  вызовов**; сейчас диффузия перестраивает битсет целиком через `geomDirty`
  (`diffusion.cpp:213-214`, `diffusion.h:275,307`).
- `bake_material_lights` уже перепекается **синхронно на карве** (`main.cpp:4022-4029`,
  `4383-4390`) — прецедент «допекание на мутации» существует, но без тайминга.
- `nav_cache` (`src/game/nav_cache.h`) полностью написан и протестирован, но в приложении
  выключен: `FloorStreamer::ensure_loaded` печёт только под `nav_bake()` — OFF по
  умолчанию (`src/game/floor_stream.cpp:352-369`).
- `parallel_for` уже принимает лимит потоков (`src/core/jobs.h:31` — параметр `threads`),
  но бейки его не пробрасывают (всегда все ядра).
- Контракт карва: «никакого ребейка здесь; долг каждого запечённого слоя =
  `CarveResult::dirtyCells`» (`src/world/destruct.h:38-46`).

Ключевое наблюдение, на котором стоит весь дизайн: **оба тяжёлых бейка читают из мира
только по-клеточный предикат проходимости**. Nav: `g.mask(x,y,z).full()`
(`src/world/nav.cpp:18`); room zones: `blocked()` — функция только от SubMask самой
клетки (`src/game/room_zone.cpp:60-69`). Значит, снапшот мира для воркера — это не
132 MiB `MacroGrid`, а **два битсета по 256 KiB** (memcpy ~50 мкс). Это снимает и сырой
указатель, и `doors.frozen`, и «фриз мира» целиком.

## 2. Грязность: одно поколение мутаций + поклеточно там, где дёшево

**Один монотонный счётчик** `worldGen` (uint64, на этаж; сброс на входе):

- `++worldGen` на каждом карве с `removed > 0` — ровно два сайта: консоль
  (`main.cpp:4025`) и боевые (`main.cpp:4386`). Не по клеткам: nav/rooms всё равно
  инвалидируются целиком (`nav.h:126-129`).
- Двери **не** инкрементируют `worldGen`: nav печётся по премисе «все двери открыты»
  (`door.h:40-43`).

Каждая структура хранит `bakedGen`; «грязная» ⇔ `bakedGen != worldGen`.

**Поклеточно — только диффузия** (O(1) уже написан): `diffusion_mark_cell` вызывать
(а) на дренаже `CarveResult::dirtyCells` в обоих карв-сайтах, (б) на дренаже
`DoorSet::dirtyCells` (двери для диффузии — реальная геометрия, `diffusion.cpp:209-214`).

**Два живых битсета проходимости** (новый модуль `src/world/walk_bits.h`),
поддерживаемые инкрементально из тех же двух дренажей:
- `navOpen[i] = !mask.full()` — закон nav (`nav.cpp:18`); патчится только от карва;
- `bodyOpen[i] = !blocked(mask)` — закон room zones (`room_zone.cpp:60-69`).

Оба предиката — функции только от собственной SubMask клетки, патч O(1) честный.

## 3. Планировщик: постоянный фоновый цикл

`RebakeScheduler` (эволюция `AsyncBake`), шаг раз в кадр рядом с текущим `nav.poll()`.

**Снапшот вместо фриза.** `start_rebake()` копирует по значению: `navOpen` + `bodyOpen`
(2×256 KiB, ~50 мкс) + параметры этажа. Воркер владеет копией — сырой указатель на World
исчезает, `doors.frozen` и весь класс «мутации во время бейка» перестают существовать.
Мутации во время бейка просто оставляют `bakedGen < worldGen` после свапа — планировщик
перезапустит цикл. Ветка `droppedBake` (выброс боевых карвов) удаляется.

**Когда стартовать** (гибрид, часы — сим-тик 125 Гц, не wall-clock):
- дебаунс `kRebakeQuietSec = 3` сим-с после последней мутации (бой коалесцируется);
- жёсткий дедлайн `kRebakeDeadlineSec = 20` сим-с после **первой** незапечённой мутации;
- минимальный интервал `kRebakeMinIntervalSec = 10` между стартами.

**Приоритеты внутри задания** (один воркер): rooms (~0.1 s) → coarse (~1.9 s) → fine
(~1.8 s); `poll()` свапает каждую по мере готовности.

**Режимы задания:**
- `Fresh` (вход на этаж, нынешние 4 сайта): живой граф освобождается сразу.
- `Rebake` (фон): живой граф **не** трогается — потребители ходят по stale до свапа.
- `Prebuild` (лифт, §5).

**Отмена:** атомарный `cancel_` с проверкой в теле каждого из 64 узловых BFS
(~30 ms гранулярность) — джойн при смене этажа становится мгновенным.

## 4. Свап: атомарность

Инвариант сохраняется: живой граф пишется ровно в `poll()` на главном потоке после join.
`poll()` в топе кадра до сим-подшагов. `FineNav` — move-assign; на `Rebake`-свапе **не**
вызывать `finish_floor_nav` (пересев толпы нужен только на входе); `RoomZones` — двойной
буфер. Память: транзиентно старый+новый fine ≈ 260 MiB — обе половины живые (одна
обслуживает тик, вторую пишет воркер); печатать `resident_bytes()`.

## 5. Лифт-поездка тем же механизмом

Режим `Prebuild(floorNumber)`: игрок заперт в кабине → воркер генерит World в
нерезидентный слот (world-часть `ensure_loaded`, `floor_stream.cpp:280-370`) + nav через
nav_cache (чтение 0.1 s против бейка 3.7 s) или полный бейк на всех ядрах → по готовности
на главном потоке ecs/gpu-часть (embody_crowd, door_build, upload_all, merge мешей) →
двери открываются. Минимальная длительность поездки = max(кинематографическая константа,
фактическое время). Снапшот не нужен: воркер — единоличный владелец строящегося World.
Требуемый рефакторинг: разрез `ensure_loaded` на world/ecs половины — самый рискованный
кусок (Registry небезопасен из воркера).

## 6. Бюджет

Пробросить `threads` из `parallel_for` через все бейки. `Rebake`: `kBgThreads =
max(2, hw/2)` → ~7-8 s на 20-поточной, ~15-20 s на 8-поточной — в SLA с запасом.
`Fresh`/`Prebuild`: все ядра. Один воркер-поток, очередь глубины 1 + флаг pending.

## 7. SLA-гейт

`tests/suite_rebake.inl`, headless, `threads=2` фикс (бит-идентичность по контракту
`jobs.h:11-15`): реальный этаж → карв пробивает стену → `++worldGen` + патч битсетов →
цикл `scheduler.step()` — ассерты: (а) свап ≤ `kRebakeSlaSec = 60` сим-с; (б) после
свапа `route_step` ведёт через проём; (в) до свапа stale-чтения не падают; (г)
бит-идентичность bits-бейка против grid-бейка на немутированном этаже — пин против
дрейфа предикатов. Второй кейс: мутация во время бейка → второй цикл добирает.
