# Запечённая видимость «лампа → клетка светосетки» — дизайн

Статус: план для обсуждения с владельцем, 2026-08-18. Код не менялся.
Место в очереди: пункт 2 перф-эпика света (`markoaudit/plans/light-perf.md`),
строка №10 реестра допекания (`markoaudit/plans/async-rebake.md` §1).

Диагноз (замерен, здесь не перепроверяется): 52% GPU-кадра — пиксельные DDA-марши
теней к лампам, перекрытым стенами; окклюжна в сборе света нет вообще
(`collect_scene_lights`, `src/app/main.cpp:227` — только дистанционный
`light_reaches_view`, `main.cpp:249-255`); kFogRadius = kWorldExtent·0.5 = 128 м
(`main.cpp:248`) при максимуме тороидальной дистанции 128 м на ось почти ничего не
отсекает; аплоад «512 ближайших к камере» (`src/render/gpu_light_grid.h:35`,
`gpu_light_grid.cpp:263-284`) гасит дальние комнаты — известный дефект.
Кривая GIGA_LIGHT_BUDGET: 512 ламп → 21.7 мс, 8 → 10.5 мс; цель — качество B=512
по цене B=8.

## Железные инварианты владельца (не обсуждаются)

- **(а) Пиксельный марш живёт всегда.** `giga_shadow`
  (`shaders/shadow_march.glsl:64-97`, DDA по вокселному зеркалу) остаётся в каждом
  пикселе и каждом шаге дымки: тени от стен, пропов и свежих дыр — кадр в кадр.
  Бейк отвечает только на вопрос «может ли свет лампы В ПРИНЦИПЕ дойти до этой
  4-метровой клетки» — т.е. заменяет не тень, а СБОР кандидатов клетки.
- **(б) Ошибка всегда «посветить лишним», никогда «потерять свет».** На карве
  dirty-клетки светосетки тем же кадром расширяют свой список до «все лампы
  радиуса»; фоновый ребейк потом ужимает.
- **(в) Камеронезависимость (S7).** Видимость — функция геометрии, не камеры.
  `sort_lights_by_distance` и аплоад-кап 512 умирают; стейджинг и таблица света —
  корневой кап kRootLights = 131072 (решение владельца, light-perf.md).

## 1. Структура данных

### 1.1 Разрез источников: статические и динамические

Бейк возможен только для источников с неподвижной позицией/радиусом. По сайтам
`collect_scene_lights`:

| Источник | Сайт | Класс |
|---|---|---|
| Пропы-света (PropLight, заякорены) | `main.cpp:331-368` | **статик** |
| Светоматериалы `g_bakedFloorLights` | `main.cpp:373-376`, `light_bake.cpp:29` | **статик** |
| Сорванный/катящийся проп-свет (RagdollRoll) | `anchor_validate_step` | динамик (переезд из статик-таблицы) |
| Мобы Lampovy/Lampoglaz | `main.cpp:275-286` | динамик |
| Контейнеры | `main.cpp:289-296` | динамик (позиция статична, но их единицы — не стоит отдельного класса) |
| Снаряды/трассеры | `main.cpp:299-313` | динамик |
| Тревога самосбора | `main.cpp:260-272` | динамик |
| Фонарик из рук | `main.cpp:385+` | динамик |

Динамиков в кадре — единицы-десятки; статиков на худшем этаже (падик) — 12 552.
Ровно статики и есть 52% кадра.

**Таблица света этажа** (новая, host-visible SSBO вместо нынешнего
`lightBuf_` 16 Б + 512×48 Б, `gpu_light_grid.cpp:74-81`):

```
[0 .. staticCount)              — статики, СТАБИЛЬНЫЕ id на поколение бейка
[staticCount .. staticCount+D)  — динамический хвост, переписывается каждый кадр
```

Размер — от корневого капа: 131072 × 48 Б = 6.3 МБ (число владельца,
light-perf.md; GpuPointLight 48 Б — `gpu_light_grid.h:39-45`). Статическая часть
пишется на бейке; в кадре по статикам обновляется ТОЛЬКО `colorIntensity.w`
(мерцание `flicker_factor`, power cut, `Interactable.active` → intensity 0 —
лампа гаснет тем же кадром, id остаётся до ребейка). Биннинг интенсивность не
читает (`light_grid.comp:104` — только posRadius), поэтому мерцание и обесточка
списки не трогают — состав клетки стабилен. 12 552 flicker-вычислений на CPU в
кадре ≈ доли мс (сейчас то же самое делается после калла); при желании уедет в
шейдер — паритет `game/flicker.h == shaders/flicker.glsl` уже закон
(`main.cpp:359-362`).

### 1.2 Клетка светосетки: живой грид + запечённый грид

Живой `gridSSBO_` (64³ × 128 Б = 32 МиБ, `gpu_light_grid.cpp:83-92`) остаётся
как есть — его каждый кадр пишет `light_grid.comp`. Добавляются:

- **bakedGrid** — второй SSBO того же лейаута `GpuGridCell` (count + top-31 id,
  отсортированных по вкладу; `gpu_light_grid.h:50-54`), 32 МиБ device-local.
  Заполняется ребейком (аплоад через стейджинг + vkCmdCopyBuffer вне рендер-пасса,
  каденция — секунды, полоса копейки).
- **dirtyGen** — u32 на клетку светосетки, 64³ × 4 Б = 1 МиБ host-visible.
  Семантика: поколение мутаций `g_worldGen` (`main.cpp:185`), при котором клетку
  запачкал карв. Шейдер получает пушем `bakedGen` (поколение, вошедшее в
  снапшот последнего свапнутого бейка) и считает клетку грязной ⇔
  `dirtyGen[cell] > bakedGen`. Очистка флагов не нужна вовсе — свап просто
  поднимает `bakedGen`. Клетки, запачканные ПОСЛЕ снапшота, автоматически
  остаются грязными до следующего свапа — класс гонок «мутация во время бейка»
  не существует по построению (тот же приём, что `bakedGen != worldGen` в
  async-rebake.md §2).

`light_grid.comp` из «биннинга всех ламп» превращается в **слияние**:

```
клетка чистая:  список = bakedGrid[cell] (уже top-31 по вкладу)
                + вставка динамического хвоста дистанционным тестом
                  (существующий top-K по d²/r², light_grid.comp:107-133)
клетка грязная: список = полный дистанционный биннинг ПО ВСЕЙ статик-таблице
                (нынешний тайловый цикл light_grid.comp:101-136) + динамики
                — это и есть «все лампы радиуса» из инварианта (б)
```

Тайловый цикл по статикам для чистых воркгрупп пропускается целиком; решение
«есть ли в воркгруппе грязные клетки» принимается воркгруппо-однородно (shared
OR до цикла), иначе `barrier()` в неоднородном контроле — UB.

### 1.3 Плотность: влезает ли 128 Б

Считаем от свойств контента, не с потолка (закон S11).

- Досягаемость лампы радиуса R до клетки: R + полудиагональ клетки светосетки
  = R + 2√3 ≈ R + 3.46 м. Для типичного R = 12 м → 15.5 м → 15.5/4 ≈ 3.9 клетки.
- Клеток на лампу ≈ (4/3)π·3.9³ ≈ **240**.
- Пар лампа×клетка на падике: 12 552 × 240 ≈ **3.0 млн**.
- Средняя плотность ДО окклюжна: 3.0 млн / 262 144 клеток ≈ **11.6 лампы на
  клетку** — уже в 31 влезает. Но среднее врёт: в плотном поле ламп блейма
  замерено ~200 кандидатов на клетку (`light_grid.comp:90`).
- ПОСЛЕ окклюжна типичная клетка видит лампы своей комнаты плюс сквозь проёмы:
  порядка 1-10. Худшие — залы/атриумы блейма: реально >31 достижимых.

Вывод: **128 Б остаётся**. Перелив клетки при бейке — ситуация штатная и
обрабатывается тем же приёмом, что уже живёт в шейдере: **отбор top-31 по вкладу
score = d²/r²** (`light_grid.comp:116`), но при бейке — **с печатью вслух**
(закон S11 «молча не режем»): `[light-vis] overflow: N cells > 31 reachable
(max M at x,y,z)`. Печать — это и датчик для вопроса №4 владельцу (расширять ли
клетку до 256 Б). Индексы u32 в статик-таблицу — 131072 влезает с запасом.

Память итого: bakedGrid 32 МиБ + dirtyGen 1 МиБ + таблица 6.3 МБ ≈ **+39 МиБ
VRAM** к нынешним 32 МиБ живого грида. CPU-сторона бейка: CSR-списки до
окклюжна ≤ 3.0 млн × 4 Б ≈ 12 МБ транзиентно в воркере.

## 2. Алгоритм бейка

### 2.1 Чем трассировать: марш от лампы, консервативность

Геометрия бейка — **только цельные макроклетки** (2 м): битсет
`fullCell[i] = mask.full()`, 128³ бит = **256 КиБ** (тот же класс снапшота, что
`navOpen` в async-rebake.md §0). Частичные клетки в бейке НЕ блокируют — это
осознанная консервативность: решётка, дыра, полустена пропускают свет в списки,
а точную тень по субвокселям кадр в кадр даёт живой `giga_shadow`
(`shadow_march.glsl:42-60` — суб-DDA частичных клеток). Пропы и двери в битсете
отсутствуют → блокировать бейк не могут → тоже консервативно; двери в придачу
идут по премисе all-open, как nav (`src/game/door.h:40-43`) — тоггл двери бейк
не старит (симметрично `main.cpp:6812-6813`: worldGen двери не инкрементируют).

Три варианта трассировки, по строгости:

1. **Флуд от лампы** (BFS по не-цельным клеткам в радиусе досягаемости).
   Строго консервативен по построению: любая физическая траектория света лежит в
   связной воздушной компоненте. Дёшев: 3.0 млн посещений ≈ 30-60 мс одним
   потоком. Минус: свет «огибает углы» — коридор за поворотом получает лампу в
   список, и пиксельный марш к ней снова жгётся впустую. Ровно те перекрытые
   лампы, которые мы убиваем, флуд убивает хуже всего.
2. **Лучевой DDA лампа→клетка, 9 точек** (центр + 8 углов клетки; клетка
   достижима, если хоть один луч чист) **+ дилатация на 1 клетку светосетки**
   (достижимость расширяется на 26 соседей, в пределах дистанционной
   досягаемости). Дилатация — страховка сэмплирования: канал уже 4 м может
   пройти между 9 лучами; расширение на клетку (4 м) покрывает промах размером
   до полного шага решётки сэмплов. Это не доказательство, а инженерная ставка —
   и потому она ОБЯЗАНА жить под оракульным тестом «не потерять свет» (§6.2).
3. **Точная субвоксельная видимость** (пучок лучей по субвоксельным целям).
   ~64× дороже, и не нужна: точность всё равно принадлежит пиксельному маршу.

**Рекомендация: вариант 2**; вариант 1 — запасной, если оракул §6.2 поймает
потерю света и владелец решит не рисковать (вопрос №1).

### 2.2 Стоимость на худший этаж (падик, 12 552 лампы, R = 12 м)

Уточнение к постановке: 12 м радиуса — это 24 м диаметра = **6-7 клеток сетки в
диаметре** (не 27; 27 клеток были бы 108 м), с полудиагоналями — шар ~240 клеток
на лампу (§1.3).

- Пар лампа×клетка: 12 552 × 240 ≈ 3.0 млн.
- Лучей (вариант 2): × 9 ≈ **27 млн**.
- Шагов DDA на луч: длина ≤ 15.5 м по 2-метровым клеткам, пересечения по трём
  осям ≤ 3·(15.5/2) ≈ 23, типично ~10 → **~3·10⁸ шагов**, каждый — битовый тест
  в 256 КиБ битсете (целиком сидит в L2).
- CPU: при 3-5 нс/шаг ≈ 1-1.5 с одним потоком → **~0.15-0.3 с на hw/2 = 10
  воркер-потоках** (параллель по лампам, детерминированный merge по id — порядок
  бит-идентичен при фиксированных threads, контракт `src/core/jobs.h:11-15`).
  Для сравнения: nav-ребейк в той же машине — ~7-8 с (async-rebake.md §6).
- GPU-компьют: та же работа ~единицы мс (27 млн лучей — меньше, чем теневых
  маршей в ОДНОМ тяжёлом кадре сейчас), но: результат нужен упорядоченным
  top-31 со score, диспатчи надо чанковать по кадрам, чтобы не съесть кадр, и
  бейк выпадает из машины допекания (снапшот/поколения/своп — всё CPU-шное).

**Рекомендация: CPU в воркере RebakeScheduler** — 0.3 с прекрасно живёт в SLA
света, инфраструктура (снапшот 256 КиБ, отмена, своп в poll()) уже
спроектирована для nav. GPU-вариант держим в кармане, если контент вырастет на
порядок (вопрос №2).

### 2.3 Выход бейка

На лампу — список достижимых клеток; транспонируется в CSR клетка→лампы;
на клетку — сорт по score d²/r², обрезка top-31 с печатью переливов; результат
пакуется прямо в лейаут `GpuGridCell[262144]` (32 МиБ) и отдаётся главному
потоку на аплоад в свапе. Плюс сводка: `[light-vis] floor N: L lamps, C lit
cells, mean/max per cell, R_max, T ms` — R_max (максимальный радиус статика,
включая полудиагональ неоновых кластеров `light_bake.cpp:96-103`) нужен дренажу
карва (§3).

## 3. Дренаж карва

### 3.1 Маппинг воксель → клетка светосетки

`CarveResult::dirtyCells` — плоские индексы макроклеток 2 м
(`src/world/destruct.h:85`); клетка светосетки 4 м = **2×2×2 макроклетки**:
`lightCell = (mx>>1, my>>1, mz>>1)` (сетки соосны: обе стартуют в нуле мира,
`gpu_light_grid.cpp:288-292`).

### 3.2 Радиус консервативного расширения — вывод

Карв только УДАЛЯЕТ материю → видимость только РАСШИРЯЕТСЯ → списки только
растут; «потерять свет» карв не может по знаку операции. Какие клетки могут
получить НОВУЮ лампу через дыру в клетке C? Путь света лампа L → точка P
проходит через C и имеет длину ≤ R_L (дальше света физически нет:
`light_attenuation`, `volumetric_fog.glsl:88-91`). C лежит на отрезке L→P ⇒
dist(C,P) ≤ dist(L,P) ≤ R_L ≤ **R_max этажа**. Значит грязнить надо шар радиуса
R_max вокруг каждой карвнутой клетки — и этого ДОСТАТОЧНО, не больше и не
меньше:

```
rDirty = ceil((R_max + halfDiagMacro + halfDiagLight) / 4 м)
       = ceil((R_max + √3 + 2√3) / 4)
падик, R_max = 12 м:  ceil(17.2/4) = 5 клеток светосетки
```

R_max — не константа, а **вывод бейка из контента этажа** (печатается в сводке
§2.3): длинный неон блейма с полудиагональю кластера легко даёт R_max 20-30 м —
подставится само.

### 3.3 Механика — тем же кадром

В обоих карв-сайтах, рядом с существующими дренажами `voxelMirror.mark_dirty` +
`mark_diffusion_dirty` (консоль `main.cpp:4076-4082`, бой `main.cpp:4437-4444`):
для каждой dirty-макроклетки пройти шар rDirty по клеткам светосетки и записать
`dirtyGen[cell] = g_worldGen` в host-visible буфер. Объём: очаг карва ~1-8
макроклеток → после дилатации ~300-500 клеток светосетки, копейки CPU.

Порядок кадра гарантирует «тем же кадром» сам: карвы дренируются в сим-секции
(`main.cpp:4043+`, `4434+`) ДО записи компьюта светосетки
(`main.cpp:6778-6783`) — диспатч этого же кадра уже видит поднятые поколения, и
грязные клетки биннятся дистанционно по всей статик-таблице: свет хлынул в дыру
немедленно, лишние лампы в списке отфильтрует живой `giga_shadow`.

Стоимость грязного фолбэка (пока ребейк не ужал): грязные клетки кластеризованы
в ~8-27 воркгрупп; их тайловый цикл — 131072/256 = 512 тайлов вместо 2, т.е.
те же тесты, что сегодня делает ВЕСЬ грид на 512 лампах, но на 0.01% клеток —
суб-мс, живёт секунды до свапа. Затяжной бой с сотнями очагов постепенно дорожает
— ровно это и ужимает фоновый ребейк.

### 3.4 Смерть и рождение самих ламп на карве

`bake_material_lights` уже перепекается синхронно на карве светоматериала
(`main.cpp:4068-4069`, `4434-4436`, гейт `carve_touches_light_material`
`main.cpp:213-225`). Со статик-таблицей событие «лампа умерла/родилась»
обрабатывается без пересборки id:

- умерла (выбит неон, разбита лампочка-GpuHandoff, проп сорвался в RagdollRoll):
  intensity слота → 0 тем же кадром (слот-надгробие до ребейка); сорванный
  катящийся свет, если нужен, переезжает в динамический хвост;
- родилась (новый кластер светоматериала после карва — редко, но бывает):
  append в хвост статик-части + dirtyGen на шар её радиуса — дистанционный
  фолбэк подхватит её тем же кадром, ребейк потом впишет в bakedGrid.

Компакция таблицы (выкидывание надгробий) — только на свапе ребейка, там же
переиздаются id.

## 4. Интеграция с RebakeScheduler

Строка №10 реестра (`markoaudit/plans/async-rebake.md` §1):

| # | Структура | Где печётся | Резидент | Полный ребейк | Грязность |
|---|---|---|---|---|---|
| 10 | LightVisibility (bakedGrid + статик-таблица) | `light_vis_bake` (новый, `src/game/light_vis_bake.{h,cpp}`) | 32 МиБ GPU + 1 МиБ dirtyGen | ~0.15-0.3 с @ hw/2 (§2.2) | `dirtyGen[cell] > bakedGen`, поклеточно |

- **Снапшот**: `fullCell`-битсет 256 КиБ (можно поддерживать инкрементально из
  тех же двух карв-дренажей, как `navOpen`/`bodyOpen` — walk_bits async-rebake.md
  §2; для света предикат третий: `mask.full()`, он уже закон шейдера
  `shadow_march.glsl:83` cls==1) + копия статик-таблицы (12.5k × 48 Б ≈ 600 КБ;
  худший кап 131072 × 48 = 6.3 МБ) + `snapshotGen = g_worldGen`.
- **Режимы**: `Fresh` (вход этажа) — бейк синхронный, на всех ядрах, рядом с
  `bake_material_lights` в сборке этажа (`main.cpp:1146`): +~0.1-0.3 с к
  загрузке, которая и так печёт nav секунды. Альтернатива «стартуем со всеми
  грязными клетками» отвергнута выводом: 262144 клетки × 131072 теста =
  3.4·10¹⁰ пар на кадр — десятки мс кадра первые секунды. `Rebake` (фон) —
  в общем воркере hw/2; живой bakedGrid не трогается до свапа, потребители ходят
  по stale-спискам (консервативно-широким либо грязно-дистанционным — свет не
  теряется ни в каком окне).
- **Место в приоритетах воркера**: rooms (~0.1 с) → **light (~0.3 с)** → coarse
  (~1.9 с) → fine (~1.8 с): свет дёшев и его ужатие возвращает кадры сразу, а
  nav-stale по ТЗ владельца терпит секунды.
- **Свап** в `poll()` на главном потоке: аплоад 32 МиБ через стейджинг,
  компакция таблицы, `bakedGen = snapshotGen` в пуш. Клетки, запачканные после
  снапшота, остаются грязными автоматически (§1.2) — второй цикл добирает.
- **SLA света мягче основного**: корректность держит мгновенный фолбэк (б), у
  ребейка чисто перф-долг. Тем же констан­там дебаунса (3/20/10 сим-с) следуем
  за компанию — отдельных не заводим (минимум систем, S11); отдельный SLA-тест
  свету не нужен, достаточно ассертов §6.

worldGen уже общий (`main.cpp:185`, фаза A сделана) — свет читает его же,

## 6. Верификация

### 6.1 Пин/replay (образец GIGA_VERLET_PIN)

Образец приёма — `GIGA_VERLET_PIN=N` / `GIGA_VERLET_PIN_DUMP` в WIP-ветке
verlet_pass (`.claude/worktrees/agent-a4d979897e35a9f20/src/render/verlet_pass.cpp:58-68,451`;
план `markoaudit/plans/verlet-merge.md:309`): env-переменная фиксирует момент,
дамп пишет состояние для побайтового сравнения прогонов.

`GIGA_LIGHT_VIS_PIN=1`: после Fresh-бейка этажа напечатать FNV-хэш bakedGrid +
сводку (ламп/клеток/переливов/R_max); `GIGA_LIGHT_VIS_DUMP=prefix` — сброс CSR в
файл. Два прогона одного сида при фиксированных threads обязаны быть
бит-идентичны (детерминированный merge §2.2 + контракт `jobs.h:11-15`).
Пин в suite: испечь эталонный этаж, сверить хэш с зашитым — дрейф алгоритма
виден коммитом, как пины падика.

### 6.2 Оракул «не потерять свет» (главный тест инварианта б)

Headless suite на реальных этажах (падик, блейм): N ≈ 10⁵ случайных пар
(лампа, субвоксельная точка в радиусе). Референс — тот же DDA, что живой
`giga_shadow` (CPU-порт по SubMask). Ассерт: **референс говорит «свет доходит»
⇒ лампа обязана быть в списке клетки** (bakedGrid либо, для клетки в переливе,
в отброшенном хвосте — тогда проверяется, что вытеснивший score честно меньше).
Обратное направление НЕ ассертится — лишние лампы законны. Это тест с обратной
полярностью: сначала прогнать с намеренно сломанной дилатацией и убедиться, что
он КРАСНЫЙ (правило run-the-mutation).

### 6.3 Карв тем же кадром

Suite: этаж, тёмная клетка за стеной от лампы (ассерт: лампы нет в её списке) →
карв пробивает стену → в ЭТОМ же кадре `dirtyGen` клетки поднят и
CPU-эмуляция слияния (тот же код отбора, что шейдер) включает лампу → после
`scheduler.step()`-цикла и свапа лампа в bakedGrid, dirtyGen ≤ bakedGen.

### 6.4 A/B перф — критерий успеха

Падик, `--shot`, GPU-таймер (`GpuPass::LightGrid` + World): полный визуал (все
12 552 статика в таблице, бейк включён) обязан приблизиться к замеру **B=8 —
10.5 мс GPU-кадра** (кривая light-perf.md; сейчас B=512 = 21.7 мс). Кадры ≠
тики (`--shot` tick variance) — сравнивать GPU-мс паса, не tick=. Вторая
проверка — регресс известного дефекта: дальняя комната с лампами за пределом
«512 ближайших» обязана светиться (xray/скрин до-после).

## Уточнение владельца (ночь-2): страх костылей => строгий вариант основным

Владелец опасается приближений («оракул» звучал как костыль). Разъяснение:

игре он не живёт и ничего не стоит. Но раз есть страх — меняем рекомендацию:
ОСНОВНЫМ бейком берём математически строгий ФЛУД ОТ ЛАМПЫ (консервативность
