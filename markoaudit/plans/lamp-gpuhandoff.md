# Лампочка → GpuHandoff: путь проверен, назначение отложено на решение владельца

Разведка 2026-08-18 (агент, всё перепроверено по file:line). Вопрос стоял так:
канон S3/S5 говорит «лампочка — GpuHandoff: разбилась → всплеск осколков в пул →
свет погас», но в `props.csv` ноль строк с этим типом.

## Вердикт: код пути ЖИВ целиком, обрывов два — в данных и в триггере

Цепь `detach → очередь → GPU-пул` работает и покрыта тестом:

- ветка GpuHandoff: `prop_system.cpp:81-104` — `bursts->push(pos, dir,
  ParticleKind::Debris, 6, matId, …)` (`:99`), затем `reg.destroy(prop)` (`:102`);
- очередь дренится в GPU-пул раз за симтик: `drain_particle_bursts`
  (`main.cpp:1229-1247`, вызов `:4465`), пул 32768 (`particle_pass.h:42`);
- **снимать `PropLight` не нужно**: `reg.destroy` уносит всю сущность, коллектор
  света идёт по `view<Transform, PropLight>` (`main.cpp:303-310`) — свет гаснет
  сам. Пункт «remove<PropLight>» из плана волны 0 снят как ненужный;
- тест: `suite_props_game.inl:715-780` (+ мой тест шва рядом).

Обрывы:

1. **Данные.** Все три лампы — `RagdollRoll`: `bare_bulb`, `flood_lamp`,
   `padic_stair_bulb` (`data/props.csv:4-6`). Токен для CSV — строго `GpuHandoff`
   (`tools/gen_prop_table.py:37`), после правки обязателен перезапуск генератора —
   ctest ловит только число строк, не содержимое.
2. **Триггер «выстрел в лампу».** `check_projectile_prop_hits`
   (`prop_system.cpp:133`) — ноль вызывающих; снаряды видят тела и клетки, пропы —
   нет (`combat.cpp:1600-1627`). Сегодня лампу роняет только карв опоры рядом.

## Почему не сделал сразу (два решения владельца)

- **Осколки будут чёрными.** У всех трёх ламп `mat_id = 0` (air, albedo 0/0/0), а
  ряд `debris` тонируется материалом. Правка `mat_id → 20` (neon_tube) чинит
  осколки, но **заодно меняет материал поверхности плафона в PropPass** — видимый
  побочный эффект, который я не вправе выбирать за вас. Альтернатива — кодовый
  фолбэк «стекло при matId==0» в точке всплеска (`prop_system.cpp:89-90`).
- **Оживление выстрела — не однострочка.** Вызов надо ставить в фазу 2
  `projectile_step` (рядом с wall-chip, `combat.cpp:1918-1950`): функция делает
  `reg.destroy`, внутри активной итерации view это нельзя. Плюс поднять
  `propPassNeedsRebuild` после `projectile_step` по `cycle_count(PropDetached)`,
  иначе плафон разбитой лампы рисуется до следующего карва.

## Готовый список правок, когда решите

A. `props.csv`: `fall_mode → GpuHandoff` в трёх строках ламп; `mat_id → 20` ЛИБО
   кодовый фолбэк. B. `python3 tools/gen_prop_table.py`. C. Вызов
   `check_projectile_prop_hits` из фазы 2 `projectile_step` + гибель снаряда как у
   `h.onWall` (`combat.cpp:1710-1716`). D. `propPassNeedsRebuild` после
   `projectile_step`. E. Тесты: пин данных (три лампы = fallMode 2), кейс
   «выстрел рядом → burst>0, лампы нет, view<PropLight> пуст».
